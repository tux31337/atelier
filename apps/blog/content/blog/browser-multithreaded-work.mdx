웹 성능 이야기를 하다 보면 "브라우저는 싱글 스레드다"라는 말을 자주 듣는다. 이 말은 틀린 말은 아니지만, 그대로 외우면 금방 헷갈린다.

이미지는 여러 개가 동시에 다운로드된다. `fetch` 요청도 JavaScript가 멈춰서 기다리는 방식이 아니다. 스크롤이나 CSS 애니메이션 일부는 JavaScript가 바빠도 어느 정도 부드럽게 움직일 수 있다. 그런데 동시에 무거운 JavaScript 반복문 하나만 돌려도 페이지 전체가 멈춘 것처럼 보인다.

둘 다 맞다. 그래서 표현을 조금 나눠야 한다.

```text
브라우저 전체
  멀티 프로세스와 멀티 스레드로 움직인다.

일반적인 페이지의 JavaScript 실행
  주로 렌더러 프로세스의 메인 스레드에서 한 번에 하나씩 실행된다.
```

이 글은 이 차이를 정리한다. 브라우저가 어떤 일을 메인 스레드 밖에서 병렬로 처리하고, 어떤 일은 다시 메인 스레드로 돌아오는지 따라가면 성능 병목을 보는 눈도 조금 선명해진다.

## 브라우저 전체는 하나의 스레드가 아니다

현대 브라우저는 보통 여러 프로세스로 나뉘어 동작한다.

```text
Browser Process
  주소창, 탭, 권한, 다운로드, 전체 브라우저 상태를 관리한다.

Renderer Process
  웹페이지의 HTML, CSS, JavaScript, DOM, 렌더링을 처리한다.

Network Service
  HTTP 요청, 캐시, 쿠키, TLS 같은 네트워크 처리를 맡는다.

GPU Process
  화면 합성, 그래픽 가속, WebGL 같은 작업을 맡는다.

Extension Process
  브라우저 확장 프로그램을 별도로 실행한다.
```

이 구조 덕분에 어떤 탭 하나가 멈춰도 브라우저 전체가 같이 죽지 않을 수 있고, 서로 다른 사이트를 격리해 보안 위험도 줄일 수 있다.

여러 탭을 열었을 때도 이 구조가 중요하다. `a.com` 탭과 `b.com` 탭은 보통 서로 다른 렌더러 프로세스에서 실행될 수 있다. 다만 "탭 하나당 무조건 렌더러 프로세스 하나"처럼 고정된 규칙은 아니다. 브라우저의 사이트 격리 정책, 메모리 상태, iframe 구성에 따라 달라질 수 있다.

중요한 것은 이것이다.

```text
브라우저 앱 전체가 하나의 스레드에서 모든 탭과 모든 다운로드를 순서대로 처리하는 구조는 아니다.
```

브라우저는 애초에 많은 일을 동시에 처리하도록 만들어져 있다.

## 한 페이지의 중심에는 메인 스레드가 있다

그럼 "브라우저는 싱글 스레드다"라는 말은 어디서 나온 걸까. 보통은 웹페이지 하나 안의 JavaScript와 DOM 중심 작업을 가리키는 말이다.

렌더러 프로세스 안에는 여러 스레드가 있을 수 있지만, 페이지의 핵심 작업은 메인 스레드에 모이는 경우가 많다.

```text
메인 스레드가 주로 맡는 일
  JavaScript 실행
  이벤트 핸들러 실행
  DOM 조작
  스타일 계산
  레이아웃 계산
  일부 페인트 작업
```

그래서 이런 코드는 페이지를 멈춘 것처럼 만든다.

```js
const start = performance.now();

while (performance.now() - start < 5000) {
  // 5초 동안 메인 스레드를 붙잡는다.
}
```

이 5초 동안 JavaScript 콜 스택은 비지 않는다. 브라우저는 클릭 이벤트를 처리하거나, DOM 변경을 반영하거나, 화면을 자연스럽게 갱신하기 어렵다.

이 관점에서 보면 "JavaScript는 싱글 스레드처럼 실행된다"는 말이 맞다. 일반적인 JavaScript 코드는 동시에 여러 줄이 병렬로 실행되지 않는다. 지금 실행 중인 작업이 끝나야 다음 작업이 실행된다.

## 네트워크 요청은 메인 스레드가 직접 다운로드하지 않는다

이미지 다운로드를 생각해보자.

```html
<img src="/a.jpg" alt="" />
<img src="/b.jpg" alt="" />
<img src="/c.jpg" alt="" />
<img src="/d.jpg" alt="" />
<img src="/e.jpg" alt="" />
<img src="/f.jpg" alt="" />
```

브라우저는 HTML을 파싱하다가 이미지들을 발견하면 네트워크 요청을 시작한다. 이때 메인 JavaScript 스레드가 이미지 바이트를 하나하나 받아오는 것이 아니다. 브라우저의 네트워크 계층이 요청을 처리한다.

흐름은 대략 이렇다.

```text
렌더러가 img 태그를 발견한다.
  -> 브라우저 네트워크 계층에 요청을 맡긴다.
  -> 여러 이미지 요청이 동시에 진행될 수 있다.
  -> 응답이 도착하면 이미지 디코딩과 렌더링 파이프라인으로 이어진다.
  -> 필요한 콜백과 DOM 반영은 다시 메인 스레드와 엮인다.
```

그래서 이미지는 보통 여러 개가 동시에 다운로드된다. DevTools의 Network 탭에서 이미지 요청들의 Waterfall 막대가 같은 시간대에 겹쳐 보이면 병렬로 받고 있는 것이다.

다만 이 말은 "이미지마다 JavaScript 스레드가 하나씩 생긴다"는 뜻이 아니다.

```text
정확한 표현
  브라우저는 내부 네트워크 처리 영역을 이용해 여러 리소스 요청을 병렬로 처리한다.

틀리기 쉬운 표현
  JavaScript 메인 스레드가 이미지마다 스레드를 만들어 다운로드한다.
```

JavaScript는 요청을 만들거나 콜백을 실행할 수 있지만, 다운로드 자체를 붙잡고 기다리는 주체는 아니다.

## 브라우저의 병렬 다운로드에는 제한이 있다

이미지를 동시에 받을 수 있다고 해서 무한정 동시에 받는 것은 아니다. 브라우저는 요청을 큐에 넣고, 프로토콜과 우선순위에 따라 스케줄링한다.

HTTP/1.1에서는 같은 도메인에 대해 브라우저가 여는 동시 연결 수가 제한적이다. 보통 6개 안팎으로 이해하면 된다. 이미지가 100개 있어도 같은 CDN 도메인에 대해 100개 연결을 한 번에 전부 여는 식으로 동작하지 않는다.

```text
HTTP/1.1 예시
  cdn.example.com에 이미지 20개 요청
  -> 브라우저가 일부 요청만 동시에 보냄
  -> 끝난 요청이 생기면 대기 중인 다음 요청을 보냄
```

HTTP/2와 HTTP/3에서는 감각이 조금 달라진다. 여러 요청을 하나의 연결 안에서 동시에 흘려보내는 multiplexing이 가능하기 때문이다. 이때는 "도메인당 연결 6개"보다 "한 연결에서 동시에 열 수 있는 스트림 수"와 브라우저의 우선순위 스케줄링이 더 중요해진다.

하지만 결론은 같다.

```text
CDN이 1000개 동시 요청을 받아줄 수 있어도
한 사용자의 브라우저가 무제한 병렬 다운로드를 하지는 않는다.
```

게다가 사용자의 네트워크 대역폭은 정해져 있다. 이미지를 6개 동시에 받든 60개 동시에 받든, 결국 그 대역폭을 나눠 쓴다. 너무 많은 요청을 한꺼번에 밀어 넣으면 첫 화면에 중요한 이미지가 늦어지거나, 디코딩과 렌더링 비용이 뒤에서 몰릴 수 있다.

## CDN은 브라우저의 요청을 빠르게 끝내주는 쪽이다

CDN을 구현하거나 설정할 때 헷갈리기 쉬운 지점이 있다.

CDN이 브라우저에게 "이미지 6개를 지금 가져가"라고 밀어주는 구조가 아니다. 보통은 브라우저가 HTML, CSS, JavaScript를 보고 필요한 리소스를 발견한 뒤 요청한다.

```text
브라우저
  이 이미지들이 필요하니 동시에 몇 개 요청하겠다.

CDN
  도착한 요청을 제한하지 않고, 캐시에서 빠르게 응답하겠다.
```

CDN 쪽에서 중요한 것은 이런 조건이다.

```text
같은 사용자에게서 온 동시 요청을 과하게 막지 않는다.
캐시 hit가 나면 origin까지 가지 않고 edge에서 응답한다.
각 이미지 요청을 독립적으로 처리한다.
HTTP keep-alive, HTTP/2, HTTP/3를 지원한다.
이미지별 URL과 cache key를 명확하게 관리한다.
rate limit을 너무 낮게 잡지 않는다.
```

HTTP/1.1 시대에는 브라우저의 도메인당 연결 제한을 피하려고 `img1.example.com`, `img2.example.com`처럼 CDN 도메인을 나누는 domain sharding을 쓰기도 했다. 하지만 HTTP/2와 HTTP/3에서는 보통 하나의 CDN 도메인에서 multiplexing과 캐시 효율을 살리는 편이 더 낫다.

요즘 CDN 최적화의 중심은 "무조건 동시에 많이"가 아니다.

```text
가까운 edge에서
작은 이미지로
캐시 hit를 만들고
중요한 리소스를 먼저 끝내는 것
```

브라우저가 병렬 요청을 할 수 있게 두되, 중요한 요청이 빨리 끝나도록 돕는 쪽이 더 현실적인 최적화다.

## 이미지 디코딩도 비용이다

이미지 파일을 다운로드했다고 바로 화면에 그릴 수 있는 것은 아니다. JPEG, PNG, WebP, AVIF 같은 파일은 화면에 표시할 수 있는 픽셀 데이터로 디코딩되어야 한다.

브라우저는 이미지 디코딩을 메인 스레드 밖에서 처리할 수 있다. 하지만 큰 이미지가 많으면 여전히 문제가 된다.

```text
다운로드 비용
  네트워크로 파일을 받는 시간

디코딩 비용
  압축된 이미지 파일을 픽셀 데이터로 푸는 시간

메모리 비용
  디코딩된 픽셀 데이터를 들고 있는 비용

렌더링 비용
  화면에 칠하고 합성하는 비용
```

그래서 이미지 최적화는 단순히 "CDN이 빠르다"로 끝나지 않는다.

```html
<img
  src="/photo-800.webp"
  srcset="/photo-400.webp 400w, /photo-800.webp 800w, /photo-1200.webp 1200w"
  sizes="(max-width: 600px) 400px, 800px"
  loading="lazy"
  alt=""
/>
```

화면 크기에 맞는 이미지를 주고, 첫 화면 밖 이미지는 늦게 요청하고, 필요한 경우 첫 화면 핵심 이미지만 우선순위를 높이는 식으로 조절해야 한다.

```html
<img src="/hero.webp" fetchpriority="high" alt="서비스 첫 화면" />
```

`fetchpriority="high"`는 정말 중요한 이미지에만 써야 한다. 모든 이미지에 높은 우선순위를 주면 결국 아무것도 특별히 중요하지 않은 상태가 된다.

## 컴포지팅과 GPU 작업은 메인 스레드 밖에서 도와줄 수 있다

브라우저는 화면을 여러 레이어로 나누고 마지막에 합성할 수 있다. 이 합성 작업에는 컴포지터 스레드와 GPU 프로세스가 관여할 수 있다.

그래서 애니메이션에서 `transform`과 `opacity`가 자주 권장된다.

```css
.box {
  transform: translateX(100px);
  opacity: 0.5;
}
```

이 속성들은 많은 경우 Layout과 Paint를 크게 다시 하지 않고 Composite 단계에서 처리될 수 있다. 반대로 다음 속성들은 배치나 칠하기 비용을 더 쉽게 만든다.

```css
.box {
  width: 300px;
  top: 100px;
  box-shadow: 0 20px 80px rgb(0 0 0 / 0.4);
}
```

`width`, `height`, `top`, `left`, `margin`처럼 배치를 바꾸는 속성은 Layout으로 이어질 수 있다. 큰 `box-shadow`, `filter`, `blur` 같은 효과는 Paint 비용을 키울 수 있다.

주의할 점은 GPU를 쓰면 무조건 빠르다는 뜻이 아니라는 것이다. 레이어가 많아지면 메모리를 더 쓰고, CPU와 GPU 사이의 데이터 이동 비용도 생긴다.

```text
좋은 방향
  움직임과 투명도 애니메이션에는 transform, opacity를 우선 고려한다.

주의할 점
  will-change를 남발하지 않는다.
  레이어를 너무 많이 만들지 않는다.
  큰 blur나 그림자를 무겁게 반복하지 않는다.
```

브라우저가 메인 스레드 밖에서 도와줄 수 있는 형태로 작업을 주는 것이 중요하다.

## 스크롤은 일부 비동기 처리될 수 있다

브라우저는 일부 스크롤을 메인 스레드와 분리해서 처리할 수 있다. 그래서 JavaScript가 조금 바빠도 스크롤이 완전히 멈추지 않는 경우가 있다.

하지만 스크롤 이벤트에서 무거운 작업을 계속 실행하면 결국 메인 스레드가 바빠진다.

```js
window.addEventListener("scroll", () => {
  heavyWork();
});
```

특히 `touchmove`나 `wheel` 이벤트에서 `preventDefault()`를 호출할 가능성이 있으면 브라우저는 스크롤을 바로 진행해도 되는지 기다려야 할 수 있다.

그래서 스크롤을 막을 의도가 없다면 passive listener를 고려한다.

```js
window.addEventListener(
  "touchmove",
  () => {
    // 스크롤을 막지 않는 짧은 작업
  },
  { passive: true },
);
```

무한 스크롤이나 요소 노출 감지는 직접 스크롤 위치를 계속 계산하기보다 `IntersectionObserver`를 우선 고려하는 편이 좋다.

```js
const observer = new IntersectionObserver((entries) => {
  for (const entry of entries) {
    if (entry.isIntersecting) {
      loadMore();
    }
  }
});
```

브라우저가 더 적절한 타이밍에 관찰 작업을 처리할 수 있기 때문이다.

## Web Worker는 JavaScript를 메인 스레드 밖으로 옮긴다

일반 JavaScript는 메인 스레드에서 실행되지만, Web Worker를 쓰면 별도 스레드에서 JavaScript를 실행할 수 있다.

```js
const worker = new Worker("/worker.js");

worker.postMessage({ numbers: [1, 2, 3] });

worker.onmessage = (event) => {
  console.log(event.data);
};
```

`worker.js`는 대략 이렇게 생길 수 있다.

```js
self.onmessage = (event) => {
  const result = event.data.numbers.reduce((sum, value) => sum + value, 0);

  self.postMessage(result);
};
```

Worker는 무거운 계산을 메인 스레드 밖으로 옮길 때 유용하다.

```text
Worker가 어울리는 작업
  대량 데이터 정렬
  큰 JSON 파싱 뒤 가공
  이미지나 영상 처리 일부
  압축
  암호화
  WASM 기반 계산
```

하지만 Worker도 공짜는 아니다.

```text
Worker의 주의점
  DOM에 직접 접근할 수 없다.
  메인 스레드와 메시지로 통신해야 한다.
  큰 데이터를 복사하면 비용이 크다.
  Worker를 너무 많이 만들면 오히려 부담이 된다.
```

큰 `ArrayBuffer` 같은 데이터는 복사 대신 소유권을 넘기는 Transferable Object를 고려할 수 있다.

```js
const buffer = new ArrayBuffer(1024);

worker.postMessage(buffer, [buffer]);
```

이렇게 하면 데이터를 복사하지 않고 worker 쪽으로 넘길 수 있다. 대신 넘긴 뒤 원래 쪽에서는 그 버퍼를 사용할 수 없다는 점을 기억해야 한다.

## Service Worker는 네트워크와 캐시에 끼어든다

Service Worker도 worker의 한 종류지만, 페이지의 계산을 대신하는 Web Worker와 역할이 다르다. 주로 네트워크 요청을 가로채고, 캐시 전략을 적용하고, 오프라인 경험을 만들 때 사용한다.

```js
self.addEventListener("fetch", (event) => {
  event.respondWith(fetch(event.request));
});
```

Service Worker는 페이지와 별도로 살아 있기 때문에 강력하다. 하지만 그만큼 캐시 전략을 잘못 짜면 오래된 파일을 계속 보여주거나, 배포 후 파일이 갱신되지 않는 문제를 만들 수 있다.

```text
Service Worker 주의점
  HTTPS 환경을 기준으로 생각해야 한다.
  캐시 무효화 전략이 필요하다.
  업데이트 타이밍이 직관적이지 않을 수 있다.
  모든 요청을 가로채면 디버깅이 어려워진다.
```

캐시를 붙이는 순간 성능 문제만이 아니라 배포 문제도 같이 다루게 된다.

## 결국 사용자가 체감하는 병목은 메인 스레드로 돌아온다

브라우저는 네트워크, 디코딩, 합성, GPU, Worker 등 많은 일을 메인 스레드 밖에서 처리할 수 있다. 하지만 사용자가 체감하는 반응성은 여전히 메인 스레드 상태에 크게 좌우된다.

다음 작업들은 메인 스레드를 바쁘게 만들기 쉽다.

```text
오래 실행되는 JavaScript
큰 DOM 변경
잦은 Layout 강제 계산
무거운 이벤트 핸들러
큰 JSON 파싱
과도한 React 렌더링
복잡한 스타일 재계산
```

예를 들어 이런 패턴은 조심해야 한다.

```js
for (const item of items) {
  item.style.width = "200px";
  console.log(item.offsetWidth);
}
```

스타일을 바꾼 직후 `offsetWidth`를 읽으면 브라우저는 최신 레이아웃 값을 알려주기 위해 계산을 앞당겨야 할 수 있다. 이 읽기와 쓰기가 반복되면 Layout 비용이 커진다.

더 나은 방향은 읽기와 쓰기를 나누는 것이다.

```js
const widths = items.map((item) => item.offsetWidth);

items.forEach((item, index) => {
  item.style.width = `${widths[index] + 20}px`;
});
```

작은 차이처럼 보이지만, 브라우저가 일을 모아서 처리할 여지를 준다.

## 실무에서 기억할 기준

브라우저의 멀티 스레드 구조를 볼 때 중요한 기준은 "어디까지가 병렬이고, 어디서 다시 메인 스레드로 돌아오는가"다.

```text
네트워크 요청
  메인 스레드 밖에서 병렬로 진행될 수 있다.
  응답 후 콜백과 DOM 반영은 메인 스레드와 엮인다.

이미지 다운로드와 디코딩
  병렬 처리될 수 있다.
  큰 이미지는 디코딩, 메모리, Paint 비용을 만든다.

Composite와 GPU 작업
  메인 스레드 밖의 도움을 받을 수 있다.
  레이어와 GPU 메모리 비용을 남발하면 안 된다.

스크롤
  일부는 비동기 처리될 수 있다.
  무거운 scroll handler는 여전히 페이지를 느리게 만든다.

Web Worker
  JavaScript 계산을 메인 스레드 밖으로 옮길 수 있다.
  DOM 접근과 메시지 비용을 고려해야 한다.

Service Worker
  네트워크와 캐시를 제어할 수 있다.
  캐시 무효화와 업데이트 전략이 중요하다.
```

성능 최적화에서 "브라우저는 멀티 스레드니까 괜찮다"는 결론은 위험하다. 병렬 처리되는 부분이 있더라도, 마지막에 DOM을 바꾸고 화면을 갱신하고 이벤트 콜백을 실행하는 일은 다시 메인 스레드에 모일 수 있다.

<Callout title="한 줄로 정리하기">
브라우저 전체는 멀티 프로세스와 멀티 스레드로 움직인다. 하지만 페이지의 JavaScript, DOM, 레이아웃 중심 작업은 메인 스레드에 모이기 쉽다. 그래서 성능 최적화는 병렬 처리에 기대는 일이 아니라 메인 스레드를 덜 막고 중요한 리소스를 먼저 끝내는 일이다.
</Callout>

이 관점이 잡히면 이미지 병렬 다운로드도 덜 헷갈린다. 브라우저는 여러 이미지를 동시에 요청할 수 있다. CDN은 그 요청들을 빠르게 받아주고 캐시에서 응답해야 한다. 하지만 브라우저의 병렬 처리량과 사용자의 네트워크, 이미지 디코딩, 렌더링 비용은 여전히 한정되어 있다.

결국 빠른 페이지는 모든 것을 동시에 밀어 넣는 페이지가 아니다.

```text
필요한 것을
작게 만들고
가까운 곳에서 가져오고
중요한 것부터 끝내고
메인 스레드를 오래 붙잡지 않는 페이지
```

브라우저가 병렬로 도와줄 수 있는 일은 도와주게 하고, 메인 스레드에서만 가능한 일은 짧게 끝내는 것. 그 균형이 브라우저 성능을 이해하는 출발점이다.
