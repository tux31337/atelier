1편에서 메모이제이션 3종으로 줄인 건 "한 번의 리렌더 안에서 다시 하는 일"이었다. 무거운 계산을 캐시하고, 같은 props의 자식을 건너뛰면 commit 시간 자체가 짧아졌다.

그런데 commit 시간이 짧다고 입력이 매끄럽다는 보장은 없다. 단일 commit이 100ms 안쪽이어도, 그 commit이 진행되는 동안에는 메인 스레드가 막혀 있어 키 입력이 들어와도 그 자리에 멈춰 있다가 한꺼번에 반영된다. 사용자 입장에서는 글자가 한두 박씩 늦게 따라붙는 느낌이다.

이번 글은 그 끊김을 다루는 두 도구를 본다. **작업량은 줄지 않는다.** 무거운 리스트는 똑같이 무겁다. 다만 그 무거운 일을 **입력 뒤로 미루는** 것이 목표다.

## urgent vs transition — 한 렌더 사이클의 두 우선순위

React 동시성 모드는 업데이트를 두 부류로 본다.

- **urgent**: 입력, 클릭, 호버처럼 사용자가 직접 즉시 반응을 기대하는 업데이트. 기본 `setState`가 여기에 해당한다.
- **transition**: 그 결과로 화면의 큰 부분을 다시 그리는 후속 업데이트. interruptible — 진행 중에 urgent가 들어오면 폐기되고 새 값으로 재시작된다.

문제는 보통 한 번의 `setState`가 이 두 가지를 같이 끌고 간다는 점이다. 검색창에서 `setQuery(next)` 하나가 입력 표시 + 8,000개 리스트 갱신을 함께 수행한다. 무거운 부분이 끝날 때까지 다음 키가 못 들어간다.

`useTransition`은 두 부분을 명시적으로 쪼개서, 무거운 쪽만 transition으로 마킹한다. `useDeferredValue`는 같은 일을 derived 값 단계에서 자동으로 해준다. 둘 다 결과는 같다 — **입력은 즉시 반영되고, 무거운 갱신은 뒤따라온다.**

## `useTransition` — 입력값과 검색값을 분리한다

8,000개짜리 리스트를 검색어로 필터링한다고 해보자. 각 행에 인위적으로 commit duration을 키우는 더미 작업을 얹어, 한 번의 리스트 갱신이 메인 스레드를 충분히 오래 점유하도록 만들었다.

```tsx
// 1. setQuery 한 번이 입력 표시와 리스트 갱신을 함께 끌고 간다
function Search() {
  const [query, setQuery] = useState("");
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <HeavyList query={query} />
    </>
  );
}

// 2. 입력값과 검색값을 분리하고, 검색값 갱신만 transition으로 마킹
// HeavyList는 React.memo로 감싼다. 이게 빠지면 효과가 사라진다 — 아래에서 다시 짚는다.
const HeavyList = memo(function HeavyList({ query }) { /* ... */ });

function Search() {
  const [inputValue, setInputValue] = useState("");
  const [searchQuery, setSearchQuery] = useState("");
  const [isPending, startTransition] = useTransition();

  const onChange = (e) => {
    const next = e.target.value;
    setInputValue(next);                           // urgent
    startTransition(() => setSearchQuery(next));   // transition
  };

  return (
    <>
      <input value={inputValue} onChange={onChange} />
      {isPending && <span>갱신 중…</span>}
      <HeavyList query={searchQuery} />
    </>
  );
}
```

1번은 단일 state라 깔끔하지만, 입력과 리스트가 같은 우선순위로 묶인다. 2번은 같은 키 입력에서 두 `setState`를 호출하지만 React는 이걸 두 가지 일로 본다. `setInputValue`는 urgent로 즉시 반영해 input value가 곧장 바뀌고, `setSearchQuery`는 transition으로 들어가 interruptible 상태가 된다. 그 사이에 새 키가 들어오면 진행 중이던 transition은 폐기되고 새 값으로 다시 시작한다.

여기서 한 가지 — `HeavyList`는 반드시 `React.memo`로 감싸야 한다. urgent 렌더에서 `Search` 본문이 다시 실행되는데, 그때 `HeavyList`의 prop인 `searchQuery`는 아직 옛 값이다. `memo`가 있으면 같은 prop이라 자식 호출을 통째로 건너뛰고, urgent 렌더가 빨리 끝나서 input이 즉시 반응한다. `memo` 없이는 부모가 다시 그리면 자식도 매번 다시 호출되므로 무거운 일이 urgent 렌더 안에서 또 돌아가고, transition을 쓰는 의미가 없어진다. 1편 `useCallback`이 `React.memo`와 짝이어야 했던 그 패턴이 여기서도 그대로다.

OFF 패널의 검색창에 빠르게 타이핑해보면 글자가 한 박씩 늦게 표시되는 느낌이 들 것이다. commit 막대도 빨갛게 채워진다. ON 패널은 같은 데이터, 같은 필터 코드인데 input 표시가 즉시 따라오고, "갱신 중…" 뱃지가 잠깐 떴다가 사라진다. commit 막대 자체는 여전히 비슷한 길이로 그려진다 — **작업 자체는 똑같이 무겁기 때문이다.** 다만 그 무거운 일이 입력 표시를 막지 않는다.

<Callout title="`isPending`은 마지막 한 박을 메우는 표시등">
`isPending`이 true인 동안에는 화면이 사용자 입력은 받았지만 결과는 아직 옛 데이터다. 이 갭이 길어 보이지 않도록 인디케이터(스피너, "갱신 중…", 흐릿한 오버레이)를 띄우는 게 보통이다. transition을 끊임없이 폐기·재시작하는 동안에는 사실상 결과가 갱신되지 않으므로, 사용자가 "내가 친 게 반영됐나?" 하지 않도록 보조 신호가 필요하다.
</Callout>

## `useDeferredValue` — 한 값의 지연된 그림자

위 코드에서 어색한 부분은 state를 두 개로 쪼개야 했다는 점이다. 검색값은 사실 입력값과 같은 정보인데, 우선순위 분리를 위해 별도 state로 보관하고 `setSearchQuery`를 따로 호출했다.

`useDeferredValue`는 이걸 derived 값 단계에서 자동으로 처리한다. 한 값의 "지연된 그림자"를 돌려준다. urgent 렌더에서는 옛 값을, 그 다음 transition 렌더에서 새 값을 보여준다.

```tsx
// 1. query가 곧 그대로 자식의 prop이다 — 입력과 리스트가 한 묶음
function Search() {
  const [query, setQuery] = useState("");
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <HeavyList query={query} />
    </>
  );
}

// 2. deferred 값을 자식에게 넘긴다. 자식은 React.memo로 감싼다.
const HeavyList = memo(function HeavyList({ query }) { /* ... */ });

function Search() {
  const [query, setQuery] = useState("");
  const deferred = useDeferredValue(query);
  const isStale = query !== deferred;
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      {isStale && <span>지연 갱신</span>}
      <HeavyList query={deferred} />
    </>
  );
}
```

순서대로 따라가 보자. `setQuery(next)`가 호출되면:

1. urgent 렌더. 부모는 `query = next`, `deferred = oldValue`로 다시 호출된다. input은 새 값으로 즉시 갱신된다.
2. `HeavyList`에 들어가는 prop은 여전히 `oldValue` — 그래서 `memo`가 얕은 비교에서 통과시켜 자식 호출을 건너뛴다.
3. React가 transition 렌더를 예약한다. 거기서 `deferred`가 `next`로 따라잡힌다. 이 렌더 동안 `HeavyList`가 실제로 새 query로 다시 그려진다.
4. 3번이 진행 중에 새 키가 들어오면 1번부터 다시 시작한다. 중간에 폐기된 작업은 사용자에게 보이지 않는다.

여기서 핵심은 **2번이 `memo` 덕분에 가능하다는 점**이다. `HeavyList`가 일반 함수 컴포넌트면 부모 리렌더만으로 자식이 다시 호출되고, deferred 값이든 query든 매 urgent 렌더마다 무거운 필터가 다시 돈다. 즉 `useDeferredValue`는 **단독으로 쓰는 hook이 아니라 `React.memo`(또는 같은 의도의 비교)와 짝으로 다닌다.** 1편의 `useCallback`과 같은 패턴이다.

## 흔한 실수

1. **모든 `setState`를 `startTransition`으로 두르기.** 입력값 자체가 transition이 되면, 사용자가 친 키가 다음 키에 의해 폐기될 수 있다. 화면에 글자가 안 찍히는 게 아니라 그냥 사라지는 것처럼 보인다. 입력 표시는 urgent로 두고, 거기서 파생되는 무거운 변경만 transition으로 분리한다.

2. **`useDeferredValue`를 받는 자식이 `memo`가 아닌 경우.** 위에서 다룬 그 자리. deferred를 만들어 봐야 자식이 매번 다시 호출되면 urgent 렌더에서도 무거운 일이 다 돌아간다. 1편의 "`useCallback` 단독은 `React.memo` 없으면 무용"과 같은 모양의 함정이다.

3. **transition 안에서 router push, 토스트 호출, fetch 같은 부수효과.** transition은 자체적으로 폐기·재시작될 수 있다. 안에서 부수효과를 호출하면 그 부수효과가 두 번 실행되거나, 폐기된 transition의 결과가 race로 도착할 수 있다. 부수효과는 transition 바깥에서 한 번만 일으킨다.

4. **`isPending`을 화면에 안 띄우기.** transition이 길어지면 사용자는 "내가 친 게 반영됐나?" 의심한다. `isPending`(또는 `useDeferredValue`에서는 `query !== deferred` 비교)으로 작은 인디케이터 하나는 띄워주는 게 보통이다. 길지 않으면 안 떠도 무방하지만, 정작 길어졌을 때 신호가 없는 게 더 큰 문제다.

## 정리, 그리고 다음 편

1편과 2편의 도구를 한 줄로 대비해 두면 머릿속에 자리잡기 쉽다.

- 1편 메모이제이션 3종 — **작업량**을 줄인다. commit 시간 자체가 짧아진다.
- 2편 transition·deferred — 작업량은 그대로 두고 **작업 시점**을 옮긴다. 무거운 일을 입력 뒤로 미룬다.

둘은 보통 같이 쓰인다. 무거운 자식은 `React.memo`로 감싸고, 거기 들어가는 값은 `useDeferredValue`로 미루고, 콜백은 `useCallback`으로 안정시킨다. 이 셋을 같이 깔아두면 입력은 항상 살아 있고, 그 사이로 무거운 결과가 따라온다.

3편에서는 React 19 신훅으로 들어간다. `useOptimistic`은 서버 응답을 기다리지 않고 결과를 먼저 보여주는 패턴, `use`는 promise를 직접 await처럼 다루는 새 hook, Actions는 폼 전송을 transition과 묶어 다루는 방식이다. 거기서는 commit 시간도 응답성도 아닌 **체감 지연**을 다룬다.
