이번 시리즈는 pnpm 모노레포 안의 프론트엔드 앱을 Docker 이미지로 만들고, Docker Compose로 실행 환경을 고정한 뒤, Nginx를 이용해 blue-green 배포 구조로 확장하고, 마지막에는 Jenkins로 CI/CD 파이프라인까지 연결하는 과정을 기록한다.

완성된 구조를 먼저 그리면 이렇다.

```text
pnpm 모노레포
  -> 특정 앱 Docker 이미지 빌드
  -> Docker Compose 실행
  -> Nginx reverse proxy
  -> blue-green 슬롯 전환
  -> Jenkins CI/CD 자동화
```

이번 글은 **1편**이다. 모노레포 안의 특정 앱을 Docker 이미지로 만들기 위해 Docker build context, pnpm workspace, 공유 패키지, Next.js standalone 출력이 어떻게 맞물리는지 정리한다.

모노레포에서 Dockerfile을 처음 쓰면 이상한 질문이 생긴다. 앱은 `apps/blog` 안에 있는데, 왜 Docker 빌드는 저장소 루트에서 해야 할까. Dockerfile도 앱 폴더 안에 있는데 왜 루트의 `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`을 먼저 복사할까. 그리고 왜 `packages/eslint-config/package.json`이나 `packages/tsconfig/package.json`까지 Dockerfile에 등장할까.

이 글은 그 질문에서 출발한다. 여기서 `apps/blog`는 첫 번째 대상 앱일 뿐이다. 중요한 주제는 블로그 자체가 아니라, pnpm 모노레포 안의 특정 프론트엔드 앱을 Docker 이미지로 만드는 흐름이다.

## 목표 구조

현재 저장소는 대략 이런 모양이다.

```text
atelier/
  apps/
    blog/
      Dockerfile
      package.json
      next.config.ts
  packages/
    ui/
      package.json
      src/
        container.tsx
    tailwind-config/
      package.json
    eslint-config/
      package.json
    tsconfig/
      package.json
  package.json
  pnpm-lock.yaml
  pnpm-workspace.yaml
```

Docker 이미지로 만들고 싶은 대상은 `apps/blog`다. 하지만 이 앱은 혼자 떨어진 npm 프로젝트가 아니다. 루트 lockfile을 공유하고, `pnpm-workspace.yaml`의 규칙 안에 있고, `packages/*` 아래의 공유 패키지를 사용할 수 있다.

예를 들어 지금 블로그 앱은 공통 레이아웃 primitive인 `Container`를 `@atelier/ui`에서 가져다 쓴다.

```tsx
import { Container } from "@atelier/ui";
```

`@atelier/ui`는 외부 npm 패키지가 아니라 같은 저장소 안의 `packages/ui`다.

그래서 Docker 빌드는 앱 폴더가 아니라 저장소 루트를 context로 삼는다.

```bash
docker build -f apps/blog/Dockerfile -t atelier-blog:test .
```

여기서 마지막 `.`이 중요하다. 이 점은 현재 디렉터리, 즉 저장소 루트를 Docker build context로 넘긴다는 뜻이다. Dockerfile은 `apps/blog/Dockerfile`을 쓰지만, Docker가 복사할 수 있는 파일 범위는 루트 전체가 된다.

루트를 context로 넘긴다고 해서 모든 파일을 이미지 빌드에 넣어도 된다는 뜻은 아니다. 그래서 `.dockerignore`도 같이 관리한다. `node_modules`, `.next`, `dist`, `.env*`, `.git` 같은 파일은 빌드 컨텍스트에서 제외한다.

```text
Docker build context
  Docker가 빌드 중 복사할 수 있는 파일 범위

.dockerignore
  그 범위 안에 있어도 빌드 컨텍스트에서 제외할 파일 목록
```

이 둘을 같이 봐야 한다. 모노레포에서는 루트 context가 필요하지만, 민감한 환경 변수 파일이나 이미 만들어진 빌드 결과물까지 context에 들어가면 빌드가 느려지고 보안상 좋지 않다.

## Dockerfile은 앱만 보는 게 아니다

현재 Dockerfile의 의존성 설치 단계는 이렇게 생겼다.

```dockerfile
FROM base AS deps
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/blog/package.json apps/blog/package.json
COPY packages/eslint-config/package.json packages/eslint-config/package.json
COPY packages/tailwind-config/package.json packages/tailwind-config/package.json
COPY packages/tsconfig/package.json packages/tsconfig/package.json
COPY packages/ui/package.json packages/ui/package.json
RUN pnpm install --frozen-lockfile --filter @atelier/blog...
```

처음 보면 `packages/eslint-config`와 `packages/tsconfig`를 Docker가 어떻게 알고 있는지 헷갈릴 수 있다. Docker가 스스로 아는 것은 없다. 우리가 `COPY`로 알려준 것이다.

pnpm은 설치할 때 루트의 `pnpm-workspace.yaml`을 본다.

```yaml
packages:
  - apps/*
  - packages/*
```

이 설정은 `apps/*`와 `packages/*` 아래의 `package.json`을 워크스페이스 패키지 후보로 본다는 뜻이다. Dockerfile에서 각 패키지의 `package.json`을 먼저 복사해두면, 컨테이너 안에서도 pnpm이 같은 모노레포 구조를 인식할 수 있다.

컨테이너 안의 `deps` 단계에서 pnpm이 보는 구조는 대략 이렇다.

```text
/repo
  package.json
  pnpm-lock.yaml
  pnpm-workspace.yaml
  apps/blog/package.json
  packages/eslint-config/package.json
  packages/tailwind-config/package.json
  packages/tsconfig/package.json
  packages/ui/package.json
```

그러면 pnpm은 `@atelier/blog`, `@atelier/eslint-config`, `@atelier/tailwind-config`, `@atelier/tsconfig`, `@atelier/ui` 같은 워크스페이스 패키지 관계를 lockfile 기준으로 설치할 수 있다.

여기서 `--filter @atelier/blog...`가 중요하다.

```bash
pnpm install --frozen-lockfile --filter @atelier/blog...
```

`@atelier/blog`는 대상 앱이다. 뒤의 `...`는 블로그 앱과 블로그 앱이 의존하는 워크스페이스 패키지까지 설치 대상으로 포함하라는 뜻이다. 모노레포 전체를 무조건 설치하는 대신, 이 이미지에 필요한 앱과 관련 패키지로 설치 범위를 좁힌다.

나중에 다른 공유 패키지가 생기고 `apps/blog`가 그 패키지를 쓰게 된다면 Dockerfile에도 같은 종류의 줄이 추가되어야 한다.

```dockerfile
COPY packages/some-package/package.json packages/some-package/package.json
```

이 줄은 UI 소스 코드를 복사하려는 목적이 아니다. 의존성 설치 단계에서 pnpm이 워크스페이스 패키지의 존재와 이름을 알 수 있게 하려는 것이다.

## 왜 전체 소스를 바로 복사하지 않을까

가장 단순한 Dockerfile은 이렇게 쓸 수도 있다.

```dockerfile
COPY . .
RUN pnpm install --frozen-lockfile
RUN pnpm -F @atelier/blog build
```

하지만 이렇게 하면 작은 코드 하나만 바뀌어도 `pnpm install` 캐시가 깨지기 쉽다. Docker는 각 명령을 layer로 쌓고, 앞 layer의 입력이 바뀌면 그 뒤 layer를 다시 실행한다.

의존성 설치에 필요한 파일은 보통 다음 정도다.

```text
package.json
pnpm-lock.yaml
pnpm-workspace.yaml
각 워크스페이스 package.json
```

반대로 페이지 컴포넌트나 CSS 파일이 바뀌어도 의존성 설치 결과는 바뀌지 않는다. 그래서 Dockerfile은 먼저 package.json 계열만 복사하고 `pnpm install`을 실행한다.

```dockerfile
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/blog/package.json apps/blog/package.json
COPY packages/eslint-config/package.json packages/eslint-config/package.json
COPY packages/tailwind-config/package.json packages/tailwind-config/package.json
COPY packages/tsconfig/package.json packages/tsconfig/package.json
COPY packages/ui/package.json packages/ui/package.json
RUN pnpm install --frozen-lockfile --filter @atelier/blog...
```

그 다음 빌드 단계에서 전체 소스를 복사한다.

```dockerfile
COPY . .
RUN pnpm -F @atelier/blog build
```

이 구조 덕분에 소스 코드만 바뀐 경우에는 의존성 설치 layer를 재사용할 가능성이 높아진다. 빌드 시간이 줄어드는 이유가 여기에 있다.

## `pnpm -F @atelier/blog build`의 의미

모노레포에서는 루트에 여러 앱과 패키지가 있을 수 있다. 하지만 이번 이미지에 필요한 것은 특정 앱 하나다.

```dockerfile
RUN pnpm -F @atelier/blog build
```

`-F`는 filter다. 워크스페이스 전체 중 `@atelier/blog` 패키지만 골라 그 패키지의 `build` 스크립트를 실행한다.

`apps/blog/package.json`에는 이런 스크립트가 있다.

```json
{
  "scripts": {
    "build": "next build"
  }
}
```

결국 Docker 빌드 안에서는 `apps/blog`의 `next build`가 실행된다. 루트는 조율자고, 실제 빌드는 대상 앱의 package.json이 맡는다.

이때 앱이 `@atelier/ui`를 import하고 있다면 Next.js 빌드는 앱 코드뿐 아니라 워크스페이스의 UI 패키지도 함께 처리해야 한다. 그래서 블로그 앱의 `next.config.ts`에는 다음 설정이 들어간다.

```ts
const nextConfig = {
  output: "standalone",
  transpilePackages: ["@atelier/ui"],
};
```

`@atelier/ui`는 빌드된 JavaScript만 제공하는 외부 패키지가 아니라 저장소 안의 TypeScript/TSX 소스 패키지다. `transpilePackages`는 이 패키지를 Next.js 빌드 파이프라인에서 함께 변환하라고 알려주는 설정이다.

## Next.js standalone 출력

Docker 실행 이미지는 작고 단순할수록 좋다. 개발용 의존성, 전체 소스, 빌드 도구를 모두 들고 있을 필요가 없다.

Next.js에서는 `next.config.ts`에 다음 설정을 넣을 수 있다.

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  output: "standalone",
};

export default nextConfig;
```

이 설정을 켜면 `next build`가 프로덕션 실행에 필요한 파일을 추적해서 `.next/standalone`에 모아준다. 그래서 최종 실행 단계에서는 다음 세 묶음만 복사한다.

```dockerfile
COPY --from=builder /repo/apps/blog/public ./apps/blog/public
COPY --from=builder /repo/apps/blog/.next/static ./apps/blog/.next/static
COPY --from=builder /repo/apps/blog/.next/standalone ./
```

`public`과 `.next/static`은 정적 파일이다. `.next/standalone`은 Next.js 서버를 실행하는 데 필요한 최소 묶음이다.

최종 실행 명령은 `next start`가 아니라 standalone 결과물의 서버 파일을 실행한다.

```dockerfile
CMD ["node", "apps/blog/server.js"]
```

여기서 헷갈리기 쉬운 지점이 있다. 빌드 단계에서는 `typescript`, `tailwindcss`, `eslint-config-next` 같은 devDependencies가 필요할 수 있다. Next.js 빌드를 수행해야 하기 때문이다. 하지만 최종 `runner` 단계는 `.next/standalone` 결과물만 복사한다. 그래서 빌드에 필요했던 개발 의존성이 최종 실행 이미지에 그대로 남지 않는다.

또한 standalone이 모든 파일을 자동으로 다 챙겨준다고 생각하면 안 된다. `public`과 `.next/static`은 별도로 복사해야 한다. 그래서 Dockerfile에 세 줄의 `COPY`가 모두 필요하다.

## 멀티 스테이지 빌드가 나누는 책임

Dockerfile은 크게 네 단계로 나뉜다.

```text
base
  Node와 pnpm 준비

deps
  의존성 설치

builder
  대상 앱 빌드

runner
  실행에 필요한 파일만 담기
```

`deps`와 `builder`에는 빌드에 필요한 도구와 소스가 들어간다. 하지만 `runner`에는 실행에 필요한 결과물만 들어간다.

이 분리가 중요한 이유는 단순하다. 이미지를 만들 때 필요한 것과 이미지를 실행할 때 필요한 것은 다르다. 빌드 도구는 build 단계에만 있으면 되고, 운영 컨테이너에는 앱 실행 파일만 있으면 된다.

## 현재 Dockerfile 전체 흐름

조각으로 보면 이해하기 쉽지만, 마지막에는 전체 파일을 한 번 이어서 보는 편이 좋다. 현재 블로그 앱의 Dockerfile은 다음 흐름이다.

```dockerfile
# syntax=docker/dockerfile:1

FROM node:24-alpine AS base
ENV NEXT_TELEMETRY_DISABLED=1
ENV PNPM_HOME="/pnpm"
ENV PATH="$PNPM_HOME:$PATH"
RUN corepack enable && corepack prepare pnpm@9.0.0 --activate
WORKDIR /repo

FROM base AS deps
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/blog/package.json apps/blog/package.json
COPY packages/eslint-config/package.json packages/eslint-config/package.json
COPY packages/tailwind-config/package.json packages/tailwind-config/package.json
COPY packages/tsconfig/package.json packages/tsconfig/package.json
COPY packages/ui/package.json packages/ui/package.json
RUN pnpm install --frozen-lockfile --filter @atelier/blog...

FROM base AS builder
COPY --from=deps /repo ./
COPY . .
RUN pnpm -F @atelier/blog build

FROM node:24-alpine AS runner
WORKDIR /app

ENV NEXT_TELEMETRY_DISABLED=1
ENV NODE_ENV=production
ENV HOSTNAME=0.0.0.0
ENV PORT=3000

RUN addgroup --system --gid 1001 nodejs \
  && adduser --system --uid 1001 nextjs

COPY --from=builder --chown=nextjs:nodejs /repo/apps/blog/public ./apps/blog/public
COPY --from=builder --chown=nextjs:nodejs /repo/apps/blog/.next/static ./apps/blog/.next/static
COPY --from=builder --chown=nextjs:nodejs /repo/apps/blog/.next/standalone ./

USER nextjs
EXPOSE 3000

CMD ["node", "apps/blog/server.js"]
```

첫 줄의 `# syntax=docker/dockerfile:1`은 Dockerfile frontend 문법을 명시한다. 지금 Dockerfile에서는 복잡한 BuildKit 기능을 쓰지 않지만, 이후 cache mount 같은 기능을 붙일 때도 이 문법 선언이 출발점이 된다.

`builder` 단계의 이 줄도 중요하다.

```dockerfile
COPY --from=deps /repo ./
```

`deps` 단계에서 설치한 `node_modules`와 pnpm workspace 구조를 builder 단계로 가져오는 역할을 한다. 그 다음 `COPY . .`로 실제 소스를 덮어 올리고, `pnpm -F @atelier/blog build`를 실행한다.

최종 컨테이너는 root가 아니라 별도의 실행 사용자로 앱을 띄운다.

```dockerfile
RUN addgroup --system --gid 1001 nodejs \
  && adduser --system --uid 1001 nextjs

USER nextjs
```

컨테이너 안에서도 앱 프로세스가 필요한 것보다 큰 권한을 갖지 않게 하기 위해서다. 작은 학습 프로젝트에서도 이 습관은 유지하는 편이 좋다.

런타임 환경 변수도 실행 이미지에서 명시한다.

```dockerfile
ENV NEXT_TELEMETRY_DISABLED=1
ENV NODE_ENV=production
ENV HOSTNAME=0.0.0.0
ENV PORT=3000
```

`NODE_ENV=production`은 프로덕션 실행 모드임을 나타낸다. `PORT=3000`은 앱 서버가 컨테이너 안에서 열 포트다. `HOSTNAME=0.0.0.0`은 컨테이너 외부에서 들어오는 연결을 받을 수 있게 한다. `localhost`로만 바인딩하면 컨테이너 안에서만 접근 가능한 서버가 될 수 있다.

`NEXT_TELEMETRY_DISABLED=1`은 Next.js telemetry를 빌드와 실행 환경에서 끈다. 기능 동작에 필요한 값은 아니지만, CI/CD 로그를 조용하게 유지하고 빌드 환경의 외부 통신을 줄이기 위해 명시했다.

## 이미지 태그는 추적 가능해야 한다

로컬에서 직접 빌드할 때는 `atelier-blog:test`처럼 단순한 태그를 붙여도 된다.

```bash
docker build -f apps/blog/Dockerfile -t atelier-blog:test .
```

하지만 CI/CD에서는 같은 태그를 계속 덮어쓰면 어떤 코드로 만든 이미지인지 추적하기 어렵다. 그래서 Jenkins 파이프라인에서는 커밋 해시를 이미지 태그로 사용한다.

```text
localhost:5000/atelier-blog:30f45bbb59f1
```

태그에 커밋 해시가 들어가면 배포된 컨테이너가 어느 커밋에서 나온 산출물인지 역추적할 수 있다. 문제가 생겼을 때 이전 이미지로 되돌리는 기준도 명확해진다.

## 빌드 성공과 실행 성공은 다르다

`docker build`가 성공했다는 말은 이미지가 만들어졌다는 뜻이다. 하지만 그 이미지로 만든 컨테이너가 실제 요청을 받을 수 있다는 뜻은 아니다.

그래서 이미지 빌드 뒤에는 최소 실행 검증이 필요하다.

```bash
docker run -d --name atelier-blog-check -p 3000:3000 atelier-blog:test
curl http://localhost:3000/api/health
docker rm -f atelier-blog-check
```

이미 내 컴퓨터에서 3000번 포트를 사용 중이라면 host port만 바꿔도 된다.

```bash
docker run -d --name atelier-blog-check -p 3010:3000 atelier-blog:test
curl http://localhost:3010/api/health
docker rm -f atelier-blog-check
```

이미지 크기도 같이 확인한다.

```bash
docker image ls atelier-blog
```

이 시리즈에서는 뒤쪽 글에서 Compose, Nginx, blue-green 배포를 붙이면서 `/api/health`를 더 적극적으로 사용한다. 실무에서도 빌드 단계와 실행 검증 단계를 분리해서 보는 편이 좋다.

## 실무 기준으로 한 번 더 보면

여기까지가 Docker 이미지 빌드의 기본 흐름이다. 실무에서는 여기에 몇 가지 기준을 더 본다.

```text
필요한 workspace만 설치하는가
빌드 캐시가 잘 유지되는가
runner 이미지에 실행 파일만 남는가
root가 아닌 사용자로 실행하는가
이미지 태그로 커밋을 추적할 수 있는가
빌드 후 컨테이너 실행과 health check를 확인하는가
이미지 크기와 취약점 스캔 결과를 확인하는가
```

더 큰 CI 환경에서는 BuildKit cache mount나 remote cache를 붙여 의존성 설치와 이미지 빌드 시간을 줄일 수 있다. 또한 `node:24-alpine`처럼 가벼운 이미지를 사용할 때는 native dependency 호환성도 빌드와 실행 검증으로 확인해야 한다. 운영 배포 전에는 Docker Scout, Trivy 같은 도구로 이미지 취약점 스캔을 붙이는 것도 일반적이다.

```bash
docker scout quickview atelier-blog:test
```

이 글에서는 이 주제들을 깊게 다루지 않는다. 1편의 목표는 모노레포의 특정 앱이 어떻게 재현 가능한 Docker 이미지가 되는지 이해하는 것이다. 캐시 고도화, 취약점 스캔, registry 정책은 CI/CD와 운영 보완 단계에서 더 자세히 다룰 수 있다.

## 실행은 Dockerfile 밖에서 정한다

Dockerfile은 이미지를 만드는 방법을 정한다. 하지만 컨테이너 이름, 포트 매핑, 여러 컨테이너의 관계는 실행 시점의 문제다.

그래서 이 저장소는 Compose도 함께 둔다.

```yaml
services:
  blog:
    container_name: atelier-blog
    image: atelier-blog:test
    build:
      context: .
      dockerfile: apps/blog/Dockerfile
    ports:
      - "3000:3000"
```

Dockerfile이 `atelier-blog:test` 이미지를 만들고, Compose가 그 이미지를 `atelier-blog` 컨테이너로 실행한다. `ports`는 내 컴퓨터의 3000번 포트와 컨테이너 안의 3000번 포트를 연결한다.

역할을 나누면 이렇게 된다.

```text
Dockerfile
  이미지를 어떻게 만들지

docker-compose.yml
  컨테이너를 어떤 이름과 포트로 실행할지
```

이 둘을 섞어서 생각하면 Docker Desktop에서 이미지 클릭 실행은 되는데 `localhost` 접속은 안 되는 상황이 쉽게 생긴다. 이미지를 만드는 것과 컨테이너를 외부에 연결하는 것은 다른 문제다.

## 정리

모노레포에서 특정 앱을 Docker 이미지로 빌드하려면 앱 폴더만 보면 부족하다. 대상 앱은 루트 lockfile, workspace 설정, 공유 패키지와 연결되어 있다.

그래서 이 구조가 필요하다.

```text
루트 build context
  -> pnpm workspace 정보 포함

package.json 선복사
  -> Docker install 캐시 활용

workspace 공유 패키지
  -> @atelier/ui 같은 앱 밖의 코드도 함께 인식

pnpm -F @atelier/blog build
  -> 특정 앱만 선택 빌드

Next.js standalone
  -> 실행 이미지에 필요한 파일 최소화
```

이미지를 만들 수 있게 되었지만, 아직 컨테이너 이름과 포트 연결은 실행 설정에 달려 있다. 다음 단계에서는 Docker Compose로 실행 환경을 파일에 고정하고, 왜 GUI 클릭 실행보다 재현성이 좋은지 정리한다.
