이번 시리즈는 pnpm 모노레포 안의 프론트엔드 앱을 Docker 이미지로 만들고, Docker Compose로 실행 환경을 고정한 뒤, Nginx를 이용해 blue-green 배포 구조로 확장하고, 마지막에는 Jenkins로 CI/CD 파이프라인까지 연결하는 과정을 기록한다.

완성된 구조를 먼저 그리면 이렇다.

```text
pnpm 모노레포
  -> 특정 앱 Docker 이미지 빌드
  -> Docker Compose 실행
  -> Nginx reverse proxy
  -> blue-green 슬롯 전환
  -> Jenkins CI/CD 자동화
```

이번 글은 **2편**이다. 1편에서 만든 Docker 이미지를 어떤 이름, 포트, 환경 변수, 네트워크로 실행할지 Docker Compose 파일에 고정한다.

Dockerfile을 만들고 나면 이미지는 만들 수 있다. 하지만 이미지를 만들 수 있다는 말과, 항상 같은 방식으로 컨테이너를 실행할 수 있다는 말은 다르다.

예를 들어 다음 값들은 Dockerfile이 아니라 컨테이너를 실행할 때 정한다.

```text
컨테이너 이름
내 컴퓨터 포트와 컨테이너 포트 연결
실행 시점 환경 변수
같이 떠야 하는 다른 컨테이너
컨테이너들이 공유할 네트워크
```

이 값들을 매번 Docker Desktop 화면에서 클릭하거나 `docker run` 옵션으로 직접 넣으면 실수하기 쉽다. 그래서 실행 설정을 `docker-compose.yml`에 남긴다. Compose는 이미지를 실행하는 방법을 파일로 고정하는 도구다.

## 이미지와 컨테이너는 다르다

이미지는 컨테이너를 만들기 위한 실행 파일 묶음이다.

```bash
docker build -f apps/blog/Dockerfile -t atelier-blog:test .
```

이 명령은 `atelier-blog:test` 이미지를 만든다. 하지만 이 명령만으로는 앱이 실행되지 않는다.

컨테이너는 이미지를 실제 프로세스로 띄운 것이다. 컨테이너를 실행할 때 비로소 포트 연결과 이름이 필요하다.

```bash
docker run --name atelier-blog -p 3000:3000 atelier-blog:test
```

처음에는 이 차이가 꽤 헷갈린다. 이미지를 만들었는데 왜 `localhost`로 접속이 안 되지, 라는 질문이 생긴다. 이유는 간단하다. 이미지는 실행된 상태가 아니고, 실행하더라도 포트가 열려 있지 않으면 내 컴퓨터에서 접근할 수 없다.

## Compose가 고정하는 것

이 저장소에서는 블로그 앱을 Compose 서비스로 둔다.

```yaml
services:
  blog-blue:
    container_name: atelier-blog-blue
    image: ${BLOG_IMAGE:-atelier-blog:test}
    build:
      context: .
      dockerfile: apps/blog/Dockerfile
    ports:
      - "127.0.0.1:3001:3000"
```

여기서 중요한 값은 네 가지다.

```text
서비스 이름: blog-blue
컨테이너 이름: atelier-blog-blue
이미지 이름: atelier-blog:test 또는 BLOG_IMAGE 값
포트 연결: 내 PC 3001 -> 컨테이너 3000
```

서비스 이름은 Compose 네트워크 안에서 쓰는 이름이다. Nginx나 Jenkins 같은 다른 컨테이너가 `blog-blue:3000`으로 접근할 수 있다.

컨테이너 이름은 Docker Desktop이나 `docker ps`에서 보이는 실제 컨테이너 이름이다. 사람이 상태를 확인할 때 좋다.

이미지 이름은 어떤 실행 파일 묶음으로 컨테이너를 만들지 정한다.

포트 연결은 내 컴퓨터에서 어느 주소로 들어오면 컨테이너 안의 어느 포트로 보낼지 정한다.

## 포트는 두 세계를 연결한다

Compose의 이 줄을 보자.

```yaml
ports:
  - "127.0.0.1:3001:3000"
```

오른쪽 `3000`은 컨테이너 안의 포트다. Next.js standalone 서버는 컨테이너 안에서 `PORT=3000`으로 실행된다.

왼쪽 `127.0.0.1:3001`은 내 컴퓨터에서 접근할 주소다. 그래서 내 PC에서는 다음 주소로 확인한다.

```bash
curl http://localhost:3001/api/health
```

하지만 같은 Compose 네트워크 안의 다른 컨테이너는 굳이 내 PC의 포트를 거치지 않는다. `blog-blue:3000`으로 직접 접근할 수 있다.

```text
내 PC에서 접근:
localhost:3001 -> blog-blue 컨테이너:3000

Compose 네트워크 안에서 접근:
blog-blue:3000 -> blog-blue 컨테이너:3000
```

이 차이는 나중에 Jenkins health check를 고칠 때 중요해진다. Jenkins가 컨테이너 안에서 실행되면 `127.0.0.1`은 내 PC가 아니라 Jenkins 컨테이너 자기 자신이기 때문이다.

## 컨테이너 이름을 고정하는 이유

학습 단계에서는 컨테이너 이름을 명시적으로 고정했다.

```yaml
container_name: atelier-blog-blue
```

이렇게 하면 상태를 확인할 때 이름이 안정적이다.

```bash
docker logs atelier-blog-blue
docker stop atelier-blog-blue
```

컨테이너 이름을 지정하지 않으면 Compose가 프로젝트명과 서비스명을 조합해서 이름을 만든다. 운영에서는 이 방식이 더 자연스러운 경우도 있지만, 지금처럼 blue-green 흐름을 손으로 따라가며 배우는 단계에서는 고정 이름이 이해를 돕는다.

## Docker Desktop GUI보다 파일이 좋은 이유

Docker Desktop에서 이미지를 클릭해서 실행할 수도 있다. 하지만 GUI 클릭은 실행 조건이 사람의 기억에 남는다.

```text
포트를 몇 번으로 열었는지
컨테이너 이름을 무엇으로 했는지
환경 변수를 넣었는지
다른 컨테이너와 같은 네트워크에 있는지
```

Compose는 이 조건을 파일로 남긴다. 그래서 다음 사람이 같은 저장소를 받아도 같은 실행 구조를 재현할 수 있다.

```bash
docker compose up --build -d blog-blue
```

이 명령은 파일에 적힌 조건대로 컨테이너를 띄운다. 명령어 옵션을 매번 길게 외우지 않아도 된다.

## Compose는 다음 단계의 발판이다

처음에는 Compose가 단순히 `docker run`을 줄여주는 도구처럼 보인다. 하지만 Nginx, registry, blue-green 배포, Jenkins까지 붙이면 Compose의 역할이 커진다.

이 저장소의 로컬 배포 환경은 대략 이렇게 된다.

```text
registry
  Docker 이미지를 저장하는 로컬 이미지 저장소

blog-blue
  블로그 앱 blue 슬롯

blog-green
  블로그 앱 green 슬롯

nginx
  외부 요청을 현재 활성 슬롯으로 넘기는 reverse proxy
```

이 컨테이너들은 같은 Compose 네트워크 안에 있다. 그래서 Nginx는 `blog-blue:3000` 또는 `blog-green:3000`으로 앱을 찾고, Jenkins는 Docker socket을 통해 같은 컨테이너 묶음을 조작한다.

## 정리

Dockerfile은 이미지를 만드는 방법을 적는다. Compose는 그 이미지를 어떤 이름, 포트, 환경, 네트워크로 실행할지 적는다.

이번 단계의 핵심은 이것이다.

```text
Dockerfile
  빌드 시점의 설명서

docker-compose.yml
  실행 시점의 계약서

ports
  내 PC와 컨테이너 포트의 연결

service name
  Compose 네트워크 안에서 컨테이너를 찾는 이름
```

컨테이너 실행이 파일로 고정되면, 이제 앱 앞에 Nginx를 세울 수 있다. 다음 글에서는 `localhost:8080 -> nginx -> blog-blue:3000` 흐름을 만들고, reverse proxy가 왜 blue-green 배포의 출발점이 되는지 정리한다.
