자바스크립트를 쓰다 보면 이런 코드를 자주 만난다.

```js
console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

Promise.resolve().then(() => {
  console.log("C");
});

console.log("D");
```

겉으로만 보면 `setTimeout`의 시간이 `0`이니까 바로 실행될 것 같다. 하지만 실제 출력은 다르다.

```text
A
D
C
B
```

이 순서를 이해하려면 자바스크립트를 "위에서 아래로 읽는 언어"로만 보면 부족하다. 위에서 아래로 실행되는 것은 맞지만, 모든 일이 같은 자리에서 바로 끝나지는 않는다.

핵심은 네 가지다.

```text
Call Stack
  지금 실행 중인 함수가 쌓이는 곳

Web API
  브라우저가 대신 기다려주는 비동기 작업 영역

Macrotask Queue
  timer, 사용자 이벤트, 네트워크 완료 같은 큰 작업이 기다리는 줄

Microtask Queue
  Promise 후속 처리처럼 지금 작업 직후 바로 이어서 처리할 일이 기다리는 줄
```

그리고 이 사이를 계속 확인하는 역할이 이벤트 루프다.

<EventLoopDiagram />

## 먼저 일반 함수는 콜 스택에서 끝난다

자바스크립트 엔진은 함수를 실행할 때 콜 스택에 올린다. 함수가 끝나면 콜 스택에서 빠진다.

```js
function third() {
  console.log("third");
}

function second() {
  third();
}

function first() {
  second();
}

first();
```

실행 흐름은 이렇게 볼 수 있다.

여기서 `global`은 특별한 함수 이름이 아니다. 파일의 바깥쪽 코드, 즉 어떤 함수 안에도 들어 있지 않은 전역 실행 문맥을 뜻한다. 브라우저가 script를 실행하기 시작하면 먼저 이 전역 코드가 콜 스택에 올라간다.

<CallStackDiagram />

여기에는 큐가 끼어들지 않는다. 그냥 지금 실행할 수 있는 함수가 콜 스택에 쌓였다가, 끝나면 빠진다.

이런 동기 코드는 앞의 코드가 끝나야 다음 코드로 넘어간다.

```js
console.log("첫 번째");
console.log("두 번째");
console.log("세 번째");
```

결과도 그대로다.

```text
첫 번째
두 번째
세 번째
```

문제는 기다림이 필요한 코드가 나올 때부터 시작된다. 타이머를 기다리거나, 사용자의 클릭을 기다리거나, 네트워크 응답을 기다리는 일은 콜 스택 안에서 계속 붙잡고 있을 수 없다.

## 브라우저는 기다리는 일을 따로 맡는다

브라우저에서 자바스크립트는 혼자 일하지 않는다. 자바스크립트 엔진 옆에는 브라우저가 제공하는 API들이 있다.

```text
JavaScript Engine
  Call Stack
  Heap

Browser
  Timer
  DOM Event
  Network
  Rendering
```

`setTimeout`, `addEventListener`, `fetch` 같은 기능은 자바스크립트 언어 자체만으로 끝나는 일이 아니다. 브라우저가 타이머를 재고, 사용자의 입력을 감지하고, 네트워크 요청을 처리한다.

예를 들어 타이머는 이렇게 움직인다.

```js
console.log("start");

setTimeout(() => {
  console.log("timer");
}, 1000);

console.log("end");
```

흐름은 이렇다.

<TimerFlowDiagram />

한 줄로 줄이면 이렇다.

```text
start 출력
  -> setTimeout callback을 브라우저 타이머에 맡김
  -> end 출력
  -> 1000ms 뒤 callback이 Macrotask Queue에 들어감
  -> Call Stack이 비면 timer 출력
```

`setTimeout` 안의 함수는 `setTimeout`을 만난 자리에서 실행되는 게 아니다. 브라우저에게 "이 시간이 지나면 이 함수를 줄에 세워줘"라고 맡기는 것에 가깝다.

## 이벤트 루프는 콜 스택과 큐를 이어준다

이벤트 루프는 이름 그대로 계속 돈다. 콜 스택이 비었는지 보고, 실행할 큐가 있는지 보고, 다음 작업을 콜 스택으로 올린다.

단순화하면 이런 흐름이다.

<EventLoopCycleDiagram />

여기서 중요한 규칙은 이것이다.

```text
현재 실행 중인 하나의 작업이 끝난다.
Call Stack이 빈다.
Microtask Queue를 먼저 전부 처리한다.
그다음 Macrotask Queue에서 다음 작업 하나를 가져온다.
이 과정을 반복한다.
```

그래서 마이크로태스크는 "가능한 한 지금 작업 직후에 이어서 처리할 일"에 가깝고, 매크로태스크는 "다음 큰 작업 차례를 기다리는 일"에 가깝다.

## 매크로태스크 큐에는 큰 작업들이 들어간다

매크로태스크 큐는 보통 task queue라고도 부른다. `macrotask`라는 말은 설명할 때 자주 쓰지만, 브라우저 표준 문서에서는 그냥 task라는 표현을 더 많이 쓴다.

매크로태스크로 들어가는 대표적인 작업은 이런 것들이다.

```text
script 전체 실행
setTimeout callback
setInterval callback
사용자 이벤트 callback
네트워크나 파일 I/O 완료 후 이어지는 작업
postMessage callback
MessageChannel callback
```

처음 HTML에서 `<script>`가 실행되는 것도 하나의 큰 작업으로 볼 수 있다. 그 script 안에서 여러 동기 함수가 실행되고, 비동기 callback들이 큐에 예약된다.

사용자 이벤트도 비슷하다.

```js
button.addEventListener("click", () => {
  console.log("clicked");
});
```

`addEventListener`를 호출하는 순간 버튼 클릭 함수가 바로 실행되는 것은 아니다. 이 코드는 브라우저에게 "이 버튼에서 click이 생기면 이 함수를 실행할 작업으로 올려줘"라고 등록하는 코드다.

<EventListenerFlowDiagram />

사용자가 버튼을 클릭하면 브라우저는 클릭 이벤트를 감지한다. 그리고 등록된 이벤트 핸들러를 실행할 작업을 큐에 넣는다.

```text
사용자 클릭
  -> 브라우저가 click 이벤트 감지
  -> click handler가 Macrotask Queue에 들어감
  -> Call Stack이 비면 이벤트 루프가 handler 실행
```

그래서 이벤트 핸들러도 그냥 마법처럼 중간에 끼어드는 게 아니다. 현재 실행 중인 자바스크립트가 끝나고, 콜 스택이 비었을 때 실행될 차례를 얻는다.

## 마이크로태스크 큐는 더 급한 후속 작업이다

마이크로태스크 큐에는 현재 작업이 끝난 직후 바로 이어서 처리해야 하는 작업이 들어간다.

대표적인 것은 이렇다.

```text
Promise.then
Promise.catch
Promise.finally
async/await의 await 이후 코드
queueMicrotask
MutationObserver callback
```

예제를 보자.

```js
console.log("start");

Promise.resolve().then(() => {
  console.log("promise");
});

console.log("end");
```

결과는 이렇게 나온다.

```text
start
end
promise
```

`Promise.resolve()`는 이미 해결된 Promise를 만든다. 그렇다고 `.then()` 안의 함수가 그 자리에서 바로 실행되지는 않는다. `.then()` callback은 마이크로태스크 큐에 들어간다.

흐름은 이렇다.

<PromiseFlowDiagram />

짧게 보면 `then` callback은 등록만 되고, 전역 코드가 끝난 뒤 마이크로태스크 큐에서 실행된다.

```text
start 출력
  -> then callback을 Microtask Queue에 등록
  -> end 출력
  -> 전역 코드 종료
  -> promise 출력
```

마이크로태스크는 "동기 코드보다 먼저"가 아니다. 동기 코드는 항상 먼저 끝난다. 다만 다음 매크로태스크로 넘어가기 전에는 마이크로태스크를 먼저 처리한다.

<Callout title="가장 중요한 순서">
동기 코드가 먼저 실행된다. 그다음 마이크로태스크가 비워진다. 그다음 매크로태스크가 하나 실행된다. 이 세 줄만 잡아도 대부분의 실행 순서 문제를 풀 수 있다.
</Callout>

## Promise와 setTimeout이 같이 있으면 Promise가 먼저다

처음 봤던 예제로 돌아가 보자.

```js
console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

Promise.resolve().then(() => {
  console.log("C");
});

console.log("D");
```

실행 과정을 조금 더 자세히 쓰면 이렇다.

<MixedTaskFlowDiagram />

순서만 압축하면 이렇게 된다.

```text
A 출력
  -> setTimeout callback은 Macrotask Queue 쪽으로 예약
  -> Promise.then callback은 Microtask Queue에 등록
  -> D 출력
  -> Microtask의 C가 먼저 출력
  -> 다음 Macrotask의 B가 출력
```

`setTimeout(..., 0)`은 "0초 뒤에 바로 실행"이 아니다. 더 정확히는 "최소한 이 작업이 끝난 뒤, 다음 태스크 차례에 실행될 수 있게 예약"에 가깝다.

그래서 Promise의 `.then()`이 먼저 출력된다.

<TaskOrderDiagram />

## async와 await도 마이크로태스크와 연결된다

`async/await`는 Promise를 더 읽기 좋게 쓰는 문법이다. `await` 뒤의 코드는 동기 코드처럼 보이지만, 실제로는 Promise가 해결된 뒤 이어지는 후속 작업이다.

```js
function getProfile() {
  return Promise.resolve("Ada");
}

async function run() {
  console.log("run start");
  const name = await getProfile();
  console.log(`run end: ${name}`);
}

console.log("script start");

run();

console.log("script end");
```

결과는 이렇게 나온다.

```text
script start
run start
script end
run end: Ada
```

`getProfile()`은 이미 해결된 Promise를 돌려주지만, `await` 뒤의 코드는 그 자리에서 바로 이어서 실행되지 않는다. `await`를 만나면 async 함수는 잠시 끊기고, 나머지 코드는 Promise가 해결된 뒤 마이크로태스크로 이어진다.

<AsyncAwaitFlowDiagram />

그래서 `await`가 있다고 해서 자바스크립트 스레드가 그 자리에서 멈춰 기다리는 것은 아니다. async 함수 안의 나머지 실행을 잠시 끊고, 현재 실행 흐름을 밖으로 돌려준다.

## 마이크로태스크는 전부 비운 뒤 넘어간다

마이크로태스크의 중요한 특징은 하나만 실행하고 끝나는 게 아니라는 점이다. 이벤트 루프는 다음 매크로태스크로 넘어가기 전에 마이크로태스크 큐를 전부 비우려고 한다.

```js
console.log("start");

setTimeout(() => {
  console.log("timeout");
}, 0);

Promise.resolve().then(() => {
  console.log("microtask 1");

  Promise.resolve().then(() => {
    console.log("microtask 2");
  });
});

console.log("end");
```

결과는 이렇게 나온다.

```text
start
end
microtask 1
microtask 2
timeout
```

첫 번째 마이크로태스크 안에서 두 번째 마이크로태스크를 새로 만들었다. 그래도 이벤트 루프는 매크로태스크로 넘어가기 전에 새로 생긴 마이크로태스크까지 처리한다.

이 특징 때문에 마이크로태스크를 너무 많이 이어 붙이면 화면 렌더링이나 사용자 이벤트 처리가 늦어질 수 있다. 더 심하면 매크로태스크 큐에 이미 들어와 있는 작업도 실행 차례를 얻지 못한다.

## 마이크로태스크가 너무 많으면 매크로태스크가 굶을 수 있다

이벤트 루프는 다음 매크로태스크로 넘어가기 전에 마이크로태스크 큐를 전부 비우려고 한다. 그래서 마이크로태스크가 실행될 때마다 다시 마이크로태스크를 추가하면 문제가 생긴다.

```js
function loop() {
  queueMicrotask(loop);
}

loop();

setTimeout(() => {
  console.log("timeout");
}, 0);
```

이 코드는 `loop`라는 마이크로태스크를 실행하고, 그 안에서 다시 `loop`를 마이크로태스크로 예약한다. 큐가 비는 순간이 오지 않는다.

<MicrotaskStarvationDiagram />

이 경우 `setTimeout` callback은 매크로태스크 큐에 들어가 있어도 실행되지 못할 수 있다. 브라우저는 "마이크로태스크를 먼저 다 비우고 다음 태스크로 넘어가야지"라고 판단하는데, 마이크로태스크가 끝없이 새로 생기기 때문이다.

`Promise.then`으로도 비슷한 상황을 만들 수 있다.

```js
function loop() {
  Promise.resolve().then(loop);
}

loop();

setTimeout(() => {
  console.log("timeout");
}, 0);
```

이런 상황을 보통 microtask starvation이라고 부른다. 마이크로태스크가 매크로태스크, 렌더링, 사용자 입력 처리를 굶기는 상태다.

그래서 긴 작업을 쪼갤 때는 목적에 맞는 양보 지점을 골라야 한다.

```text
Promise.then, queueMicrotask
  지금 작업 직후 반드시 이어서 처리해야 하는 짧은 후속 작업에 적합하다.

setTimeout, MessageChannel
  다음 태스크로 넘겨서 브라우저가 중간에 다른 일을 처리할 기회를 만들 수 있다.

requestAnimationFrame
  다음 화면을 그리기 직전에 DOM 읽기나 쓰기를 맞추고 싶을 때 적합하다.
```

Promise가 빠르고 우선순위가 높다고 해서 무한히 이어 붙여도 괜찮은 것은 아니다. 우선순위가 높다는 건 그만큼 다른 작업을 밀어낼 수 있다는 뜻이기도 하다.

## 화면 렌더링은 큐 사이에서 기회를 얻는다

브라우저는 자바스크립트만 실행하는 프로그램이 아니다. 스타일을 계산하고, 레이아웃을 만들고, 페인트하고, 화면을 갱신해야 한다.

단순화하면 한 번의 흐름은 이렇게 생각할 수 있다.

```text
Macrotask 하나 실행
  -> 그 안의 동기 코드 실행
  -> Microtask Queue 전부 비우기
  -> 브라우저가 필요하면 렌더링
  -> 다음 Macrotask 하나 실행
```

그래서 오래 걸리는 동기 작업은 화면을 막는다.

```js
button.addEventListener("click", () => {
  const start = performance.now();

  while (performance.now() - start < 3000) {
    // 3초 동안 메인 스레드를 붙잡는다.
  }

  console.log("done");
});
```

이 클릭 핸들러가 실행되는 동안 콜 스택은 비지 않는다. 브라우저는 그동안 다음 이벤트를 처리하거나 화면을 부드럽게 갱신하기 어렵다.

반대로 긴 작업을 여러 조각으로 나누면 브라우저가 중간중간 숨 쉴 틈을 얻는다.

```js
function runChunk(items) {
  const chunk = items.splice(0, 100);

  chunk.forEach(doWork);

  if (items.length > 0) {
    setTimeout(() => runChunk(items), 0);
  }
}
```

여기서 `setTimeout`을 쓰면 다음 조각은 다음 매크로태스크로 밀린다. 그 사이 브라우저는 렌더링이나 사용자 입력 처리 기회를 얻을 수 있다.

## requestAnimationFrame은 별도로 봐야 한다

실무에서 자주 만나는 `requestAnimationFrame`은 마이크로태스크도, 일반적인 매크로태스크도 아니다. 브라우저가 다음 화면을 그리기 전에 호출해주는 프레임 callback에 가깝다.

```js
requestAnimationFrame(() => {
  element.style.transform = "translateX(100px)";
});
```

이 API는 "다음 렌더링 직전에 이 작업을 해줘"라는 의미로 쓰기 좋다. 애니메이션에서 DOM 스타일을 바꾸거나, 화면 갱신 타이밍에 맞춰 작업할 때 유용하다.

실행 순서를 아주 단순하게만 보면 이렇게 잡을 수 있다.

```text
동기 코드
  -> Microtask
  -> requestAnimationFrame callback
  -> Rendering
  -> 다음 Task
```

브라우저 구현과 상황에 따라 세부 순서는 더 복잡할 수 있지만, 핵심은 `requestAnimationFrame`을 `setTimeout`의 다른 이름처럼 보면 안 된다는 점이다. 화면을 그리는 타이밍과 연결된 API다.

## 어떤 코드가 어디로 가는지 정리하기

자주 쓰는 코드들을 큐 기준으로 묶으면 이렇게 볼 수 있다.

```text
Call Stack에서 바로 실행
  일반 함수 호출
  console.log
  for, while 같은 동기 반복문
  현재 script의 동기 코드

Web API를 거쳐 Macrotask Queue로 들어감
  setTimeout
  setInterval
  사용자 이벤트 핸들러
  postMessage
  MessageChannel
  일부 네트워크, I/O 완료 후 작업

Microtask Queue로 들어감
  Promise.then
  Promise.catch
  Promise.finally
  async 함수의 await 이후 코드
  queueMicrotask
  MutationObserver

렌더링 타이밍과 연결
  requestAnimationFrame
```

`fetch`는 조금 헷갈릴 수 있다.

```js
fetch("/api/posts")
  .then((response) => response.json())
  .then((data) => {
    console.log(data);
  });
```

네트워크 요청 자체는 브라우저가 처리한다. 응답이 도착하면 Promise가 해결되고, `.then()`에 등록한 callback은 마이크로태스크로 이어진다.

그래서 `fetch`는 "네트워크는 브라우저가 기다리고, Promise 후속 처리는 마이크로태스크로 실행된다"고 이해하면 좋다.

## 실행 순서 문제는 표로 풀 수 있다

복잡한 코드를 만나면 머릿속으로만 따라가기 어렵다. 그럴 때는 콜 스택, 마이크로태스크 큐, 매크로태스크 큐를 표처럼 나눠서 적으면 된다.

```js
console.log("1");

setTimeout(() => {
  console.log("2");

  Promise.resolve().then(() => {
    console.log("3");
  });
}, 0);

Promise.resolve().then(() => {
  console.log("4");

  setTimeout(() => {
    console.log("5");
  }, 0);
});

console.log("6");
```

먼저 전역 script를 실행한다.

```text
출력
  1
  6

Microtask Queue
  4 출력, timer 5 예약

Macrotask Queue
  timer 2 실행
```

전역 script가 끝나면 마이크로태스크를 먼저 비운다.

```text
출력
  1
  6
  4

Microtask Queue
  (empty)

Macrotask Queue
  timer 2 실행
  timer 5 실행
```

그다음 매크로태스크 하나를 실행한다. 먼저 등록된 timer 2가 실행된다.

```text
출력
  1
  6
  4
  2

Microtask Queue
  3 출력

Macrotask Queue
  timer 5 실행
```

timer 2라는 매크로태스크가 끝났으니 다시 마이크로태스크를 비운다.

```text
출력
  1
  6
  4
  2
  3

Microtask Queue
  (empty)

Macrotask Queue
  timer 5 실행
```

마지막으로 timer 5가 실행된다.

```text
출력
  1
  6
  4
  2
  3
  5
```

정답을 외우기보다 이 표를 직접 그리는 습관이 더 오래 간다.

## Node.js에서는 세부 규칙이 다를 수 있다

여기까지의 설명은 주로 브라우저 환경을 기준으로 했다. Node.js에도 이벤트 루프가 있지만, 내부 단계가 더 세분화되어 있고 `process.nextTick`, I/O phase, timer phase 같은 Node.js 전용 규칙이 있다.

그래서 브라우저와 Node.js에서 아주 세밀한 순서가 달라질 수 있다.

프론트엔드 코드를 이해할 때는 먼저 브라우저 기준으로 잡으면 된다.

```text
동기 코드
  -> Microtask
  -> Rendering 기회
  -> 다음 Macrotask
```

Node.js 런타임 안에서 서버 코드를 깊게 다룰 때는 그때 Node.js 이벤트 루프의 phase를 따로 보면 된다.

## 결국 하나의 질문으로 돌아온다

자바스크립트 실행 순서를 볼 때 가장 먼저 물어볼 질문은 이것이다.

```text
이 코드는 지금 콜 스택에서 바로 실행되는가,
아니면 나중에 실행되도록 큐에 들어가는가?
```

그다음은 큐의 종류를 보면 된다.

```text
Promise 계열인가?
  -> Microtask Queue

timer나 이벤트인가?
  -> Macrotask Queue

화면 그리기 직전 작업인가?
  -> requestAnimationFrame

그냥 함수 호출인가?
  -> Call Stack에서 바로 실행
```

이 관점이 잡히면 `setTimeout(..., 0)`이 왜 늦게 실행되는지, Promise가 왜 timer보다 먼저 실행되는지, `await` 뒤의 코드가 왜 나중에 이어지는지, 긴 동기 작업이 왜 화면을 막는지 자연스럽게 이어진다.

자바스크립트는 한 번에 하나의 실행 흐름만 콜 스택에 올린다. 대신 브라우저가 기다리는 일을 맡고, 큐가 다음 실행 순서를 보관하고, 이벤트 루프가 그 사이를 연결한다.

그래서 비동기 코드를 읽는다는 건 결국 시간표를 읽는 일에 가깝다. 지금 실행되는 일, 바로 다음에 이어질 일, 다음 큰 차례를 기다리는 일을 나눠 보면 복잡한 실행 순서도 훨씬 덜 흔들린다.
