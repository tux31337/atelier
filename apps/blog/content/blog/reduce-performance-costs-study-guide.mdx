`/finding-performance-bottlenecks` 글에서는 먼저 병목을 찾는 흐름을 정리했다. 이번에는 그다음 단계로 넘어가 보려고 한다.

병목을 찾고 나면 질문이 바뀐다.

```text
그래서 무엇을 줄여야 할까?
```

이 질문에 답할 때 가장 중요한 건 모든 최적화를 한 번에 붙이지 않는 것이다. 느린 이유에 따라 줄여야 하는 비용이 다르기 때문이다.

```text
리소스가 늦게 도착한다
  -> 네트워크 비용을 본다

LCP 이미지가 너무 늦다
  -> 이미지 비용을 본다

클릭이나 스크롤이 버벅인다
  -> JavaScript 비용을 본다
```

이번 글은 이 세 가지를 공부용 관점으로 묶는다.

1. 네트워크 비용 줄이기
2. 이미지 비용 줄이기
3. JavaScript 비용 줄이기

각 항목마다 아래 순서로 보면 흐름이 잡힌다.

```text
이게 왜 필요한가
어디서 확인하는가
어떻게 줄이는가
무슨 실수를 조심해야 하는가
```

## 네트워크 비용 줄이기

네트워크 비용은 브라우저가 필요한 리소스를 받기까지 기다리는 비용이다. 파일이 크거나, 요청이 너무 많거나, 먼 서버에서 받아오거나, 다시 받아오지 않아도 되는 파일을 매번 새로 받으면 이 비용이 커진다.

Network 패널에서 보통 먼저 보는 것은 세 가지다.

```text
1. 요청 수가 많은가
2. 파일 크기가 큰가
3. 첫 화면에 필요한 리소스가 늦게 도착하는가
```

### 텍스트 압축

HTML, CSS, JavaScript, JSON 같은 텍스트 리소스는 압축 효율이 좋다. 그래서 서버는 보통 `gzip` 또는 `brotli`로 압축해서 보낸다.

왜 중요할까. 텍스트 파일은 화면을 여는 첫 순간에 거의 항상 필요하다. HTML이 늦으면 문서 자체가 늦게 오고, CSS가 늦으면 스타일이 늦고, JavaScript가 늦으면 hydration이나 상호작용 준비가 늦어진다.

확인할 때는 Network 패널에서 응답 헤더의 `content-encoding`을 본다.

```text
content-encoding: br
content-encoding: gzip
```

둘 중 하나가 보이면 압축이 켜져 있을 가능성이 높다. 일반적으로는 `brotli`가 더 잘 압축되지만, 중요한 건 특정 포맷 이름을 외우는 것보다 "텍스트 리소스가 압축 없이 그대로 오고 있지 않은가"를 먼저 보는 것이다.

공부할 때 기억해둘 기준은 이 정도면 충분하다.

```text
텍스트 리소스
  -> 압축 대상

PNG, JPEG, WebP 같은 이미지
  -> 이미 자체 압축 포맷이므로 텍스트 압축과 다른 문제
```

자주 하는 실수도 있다. 이미지를 많이 쓰는 페이지가 느린데 텍스트 압축만 켜고 끝냈다고 생각하는 경우다. 텍스트 압축은 중요하지만, 이미지 병목은 이미지 자체 최적화로 따로 봐야 한다.

### 리소스 캐싱

캐싱은 "같은 파일을 다음 방문 때 다시 받을 필요가 있는가"에 대한 이야기다.

정적 리소스가 자주 바뀌지 않는데도 매번 다시 요청하면 네트워크 비용이 반복된다. 반대로 오래 캐싱해도 되는 파일을 잘 캐싱하면 재방문 속도가 훨씬 좋아진다.

Network 패널과 응답 헤더에서 자주 보는 값은 이런 것들이다.

```text
cache-control
etag
last-modified
```

가볍게 이해하면 이렇게 정리할 수 있다.

```text
파일 이름에 해시가 붙는 정적 파일
  -> 오래 캐싱하기 좋다

자주 바뀌는 HTML 문서
  -> 무조건 오래 캐싱하면 위험할 수 있다
```

예를 들어 CSS나 JS 번들 파일이 `app.abcd1234.js`처럼 내용 기반 이름을 가진다면, 내용이 바뀔 때 파일 이름도 함께 바뀐다. 이런 파일은 길게 캐싱해도 비교적 안전하다. 반대로 HTML 문서는 최신 내용이 중요하므로 더 신중하게 봐야 한다.

캐싱은 첫 방문을 빠르게 만드는 기술만은 아니다. 재방문 비용을 줄여서 전체 체감을 낮추는 기술에 가깝다.

### preload

`preload`는 브라우저에게 "이 리소스는 곧 필요하니 조금 더 일찍 가져와도 된다"라고 알려주는 힌트다.

모든 리소스에 붙이는 것은 좋지 않다. 정말 빨리 필요한 것에만 써야 한다. 보통은 첫 화면의 핵심 폰트, LCP 이미지, 아주 이른 시점에 필요한 스타일이나 스크립트 후보를 생각한다.

좋은 질문은 이것이다.

```text
이 리소스가 첫 화면을 여는 데 정말 중요하고,
브라우저가 기본 우선순위만으로는 너무 늦게 가져오고 있는가?
```

Network Waterfall에서 해당 리소스가 너무 늦게 요청되면 `preload`를 검토해볼 수 있다.

하지만 남용하면 오히려 경쟁이 생긴다. 덜 중요한 파일까지 앞당겨 받으면 정말 중요한 파일의 대역폭을 나눠 먹기 때문이다. 그래서 `preload`는 "더 빨리 받으면 좋겠다"가 아니라 "늦게 받으면 첫 화면이 실제로 느려진다"일 때 붙이는 편이 좋다.

### CDN

CDN은 사용자와 가까운 위치에서 정적 리소스를 전달해 지연을 줄이는 방식이다. 특히 이미지, JS, CSS, 폰트처럼 여러 지역에서 반복 요청되는 파일에 효과가 크다.

공부 관점에서 CDN은 "어떤 서버를 쓰는가"보다 "정적 리소스를 사용자에게 더 가까운 곳에서 전달한다"로 이해해도 충분하다.

CDN이 주는 이점은 보통 이런 흐름으로 이해하면 된다.

```text
더 가까운 서버
  -> 왕복 시간 감소

캐시된 정적 리소스 제공
  -> 원본 서버 부담 감소

여러 지역에서 안정적으로 전달
  -> 사용자 위치 차이에 덜 민감
```

다만 CDN을 붙였다고 모든 것이 해결되지는 않는다. 파일 자체가 너무 크면 가까운 곳에서 줘도 느릴 수 있다. 그래서 CDN은 "전달 경로 최적화"이고, 압축이나 이미지 최적화는 "리소스 자체 최적화"라고 같이 구분해두면 좋다.

<Callout title="네트워크 비용은 기다림의 비용이다">
텍스트 압축은 같은 내용을 더 작게 보내는 일이고, 캐싱은 같은 파일을 덜 다시 받게 만드는 일이며, preload는 정말 중요한 파일을 먼저 받게 만드는 일이고, CDN은 더 가까운 곳에서 받게 만드는 일이다.
</Callout>

## 이미지 비용 줄이기

이미지는 성능에서 가장 자주 눈에 띄는 병목이다. 이유도 단순하다. 대개 크고, 시각적으로 중요하며, LCP 후보가 되기 쉽기 때문이다.

이미지 비용을 볼 때는 먼저 이 질문부터 던지면 좋다.

```text
이 이미지는 첫 화면에 꼭 필요한가
이 이미지 크기가 화면보다 과한가
이 이미지를 지금 당장 받아야 하는가
```

### 이미지 사이즈 최적화

원본 이미지가 너무 크면 브라우저는 큰 파일을 내려받고, 디코딩하고, 화면 크기에 맞춰 줄여 그려야 한다. 이 과정이 모두 비용이다.

흔한 실수는 이런 식이다.

```text
화면에는 800px 정도로 보이는 이미지
  -> 원본은 4000px 이상
```

이 경우 사용자는 보이지도 않는 해상도까지 함께 받고 있을 가능성이 크다.

이미지 최적화의 첫 단계는 간단하다.

```text
화면에 필요한 크기보다 과하게 큰 원본을 쓰지 않는다
파일 용도에 맞는 포맷을 쓴다
```

사진 계열은 보통 `WebP`나 `AVIF` 같은 효율적인 포맷을 먼저 떠올릴 수 있고, 단순한 그래픽은 경우에 따라 다른 선택이 맞을 수 있다. 공부 단계에서는 "무조건 이 포맷"보다 "시각 품질을 유지하면서 더 작은 파일로 보낼 수 있는가"를 기준으로 잡는 편이 낫다.

### 적절한 크기로 변환

반응형 화면에서는 같은 이미지라도 모바일과 데스크톱에 필요한 크기가 다르다. 그런데 모든 사용자에게 가장 큰 버전을 보내면 낭비가 생긴다.

그래서 중요한 개념이 "한 장의 원본을 여러 크기로 준비하고, 브라우저가 상황에 맞는 파일을 고르게 한다"는 것이다.

```text
모바일
  -> 더 작은 이미지 선택

큰 화면
  -> 더 큰 이미지 선택
```

Next.js의 `Image` 컴포넌트나 이미지 CDN이 이 문제를 많이 도와준다. 공부할 때는 내부 구현을 다 외우기보다, "화면과 기기 조건에 따라 너무 큰 이미지를 내려주지 않게 만드는 장치"라고 이해하면 된다.

이 개념은 첫 단계의 "원본이 과하게 크지 않은가"와 닮아 있지만 조금 다르다.

```text
이미지 사이즈 최적화
  -> 원본 자체가 과한지 본다

적절한 크기로 변환
  -> 사용자 상황에 맞는 버전을 내려주는지 본다
```

### 이미지 CDN

이미지 CDN은 단순히 이미지를 가까운 서버에서 주는 것만이 아니라, 요청 상황에 맞게 리사이즈, 포맷 변환, 캐싱을 함께 처리해주는 경우가 많다.

그래서 이미지 CDN은 여러 문제를 한 번에 다루는 편이다.

```text
더 가까운 전달
적절한 크기 변환
효율적인 포맷 변환
캐싱
```

이미지가 많은 서비스라면 운영 효율 면에서도 장점이 크다. 같은 원본을 두고 다양한 화면 크기와 포맷을 유연하게 제공하기 쉽기 때문이다.

### 이미지 preload

첫 화면의 가장 중요한 이미지, 특히 LCP 후보라면 `preload`를 고려할 수 있다. 대표적으로 글 상세의 hero image, 상품 상세의 대표 이미지, 메인 비주얼 이미지 같은 경우다.

여기서 핵심은 "첫 화면의 핵심 이미지"라는 점이다. 페이지 아래쪽에 있는 이미지를 preload하면 오히려 손해일 수 있다.

이때는 이렇게 생각하면 편하다.

```text
LCP 후보 이미지
  -> preload 후보

스크롤 아래 이미지
  -> preload보다 lazy load 후보
```

### Image Lazy Load

lazy load는 지금 당장 보이지 않는 이미지를 나중에 받게 해서 초기 네트워크와 렌더링 부담을 줄이는 방법이다.

특히 리스트 페이지, 블로그 홈, 갤러리, 무한 스크롤 화면처럼 이미지가 많이 등장하는 곳에서 체감이 크다.

하지만 첫 화면의 핵심 이미지까지 lazy load하면 안 된다. 그 이미지는 빨리 보여야 하기 때문이다. 그래서 lazy load는 "나중에 보여도 되는 이미지"에 쓰는 기술이다.

공부할 때 가장 많이 헷갈리는 부분이 바로 이것이다.

```text
중요한 첫 화면 이미지
  -> 빨리 받아야 한다
  -> preload 검토

첫 화면 아래 이미지
  -> 나중에 받아도 된다
  -> lazy load 검토
```

<Callout title="이미지 최적화는 LCP와 자주 연결된다">
이미지는 눈에 잘 보이고 파일도 큰 편이라 LCP 병목의 원인이 되기 쉽다. 그래서 이미지 최적화는 단순한 용량 줄이기보다, 어떤 이미지가 첫 화면에 중요하고 어떤 이미지는 늦게 받아도 되는지 구분하는 일에 가깝다.
</Callout>

## JavaScript 비용 줄이기

JavaScript 비용은 단순히 파일 다운로드 크기만 뜻하지 않는다. 받아온 뒤 파싱하고, 실행하고, hydration하고, 이벤트를 연결하는 비용까지 포함한다.

그래서 JavaScript 문제는 보통 두 군데에서 보인다.

```text
Network
  -> JS 파일이 크다

Performance
  -> 메인 스레드에서 JS 실행 시간이 길다
```

### 병목 코드 제거

가장 먼저 볼 것은 "정말 필요 없는 일을 하고 있지 않은가"다.

코드를 쪼개기 전에 불필요한 계산, 과한 상태 업데이트, 매 렌더마다 반복되는 무거운 로직, 필요 이상의 client component 범위를 먼저 의심하는 편이 좋다.

예를 들면 이런 질문들이다.

```text
이 계산은 매번 다시 해야 하는가
이 컴포넌트가 꼭 client component여야 하는가
이 이벤트 처리 안에서 무거운 루프가 돌고 있지는 않은가
이 라이브러리가 첫 화면에서 정말 필요한가
```

성능 최적화에서 흔히 놓치는 점이 있다. 번들 쪼개기는 잘했는데, 정작 클릭 한 번에 무거운 계산이 실행되면 사용자는 여전히 버벅임을 느낀다. 그래서 Performance 패널에서 긴 task를 보고 병목 함수를 좁히는 과정이 중요하다.

### React Code Splitting

code splitting은 JavaScript를 한 덩어리로 보내지 않고, 필요한 시점에 나눠 보내는 전략이다.

중요한 이유는 간단하다. 첫 화면에 필요 없는 코드까지 처음부터 모두 보내면 다운로드, 파싱, 실행 비용이 한꺼번에 커지기 때문이다.

공부할 때는 이렇게 이해하면 된다.

```text
지금 당장 필요한 코드
  -> 초기 번들

특정 화면, 특정 상호작용에서만 필요한 코드
  -> 나중에 로드
```

예를 들어 댓글 에디터, 차트, 3D 뷰어, 복잡한 에디팅 패널처럼 무거운 기능은 첫 화면에서 바로 필요하지 않을 수 있다. 이런 코드는 분리 후보가 된다.

중요한 건 "모든 것을 잘게 쪼개기"가 아니다. 너무 잘게 나누면 요청 관리가 복잡해지고, 사용자 동선에 따라 오히려 전환 시점이 어색해질 수도 있다. 그래서 code splitting은 "초기 로딩에 꼭 필요하지 않은 큰 코드"부터 생각하는 편이 좋다.

### Component Lazy Load

컴포넌트 lazy load는 code splitting의 구체적인 적용 장면이라고 보면 이해가 쉽다. 무거운 컴포넌트를 처음부터 렌더링 경로에 넣지 않고, 필요할 때 불러오는 방식이다.

대표적인 예시는 이런 것들이다.

```text
접었을 때 보이지 않는 상세 패널
모달이 열릴 때만 필요한 UI
화면 아래쪽에 늦게 등장하는 인터랙티브 위젯
관리자 전용 도구 패널
```

다만 사용자 동선상 거의 바로 열릴 요소라면 무조건 늦게 불러오는 것이 정답은 아니다. 버튼을 눌렀을 때 너무 오래 기다리게 만들 수도 있기 때문이다. 그래서 lazy load는 "처음엔 필요 없지만, 나중에 필요한가"를 보는 전략이다.

### 컴포넌트 preload

여기서 `preload`가 다시 등장한다. 처음부터 렌더링하지는 않지만, 사용자가 곧 진입할 가능성이 높은 컴포넌트라면 미리 가져오는 전략을 쓸 수 있다.

예를 들면 이런 상황이다.

```text
탭 전환 직후 높은 확률로 열릴 패널
hover 뒤 곧바로 열릴 메뉴
다음 화면으로 이동하면 거의 반드시 필요한 코드
```

이 방식은 lazy load와 반대가 아니라 보완 관계다.

```text
lazy load
  -> 지금은 렌더링하지 않는다

preload
  -> 하지만 곧 필요할 가능성이 높으니 미리 받아둘 수 있다
```

그래서 JavaScript 최적화는 종종 이 균형을 잡는 일이다.

```text
너무 일찍 받으면
  -> 초기 비용 증가

너무 늦게 받으면
  -> 상호작용 시 대기 증가
```

<Callout title="JavaScript 비용은 다운로드로 끝나지 않는다">
JS 파일이 작아도 실행 비용이 크면 느릴 수 있고, 반대로 실행은 가벼워도 초기 번들이 너무 크면 첫 로딩이 느릴 수 있다. 그래서 Network와 Performance를 같이 봐야 한다.
</Callout>

## 세 가지를 함께 보는 기준

지금까지 네트워크, 이미지, JavaScript를 따로 나눠 봤지만 실제 페이지에서는 서로 얽혀 있다.

예를 들어 첫 화면이 느릴 때는 이런 경우가 섞여 있을 수 있다.

```text
LCP 이미지가 너무 크다
폰트가 늦게 온다
초기 JS가 커서 hydration이 늦다
```

그래서 실전에서는 아래처럼 연결해서 생각하는 편이 좋다.

```text
첫 화면이 늦다
  -> LCP 요소가 텍스트인지 이미지인지 본다
  -> Network에서 해당 리소스 도착 시점을 본다
  -> Performance에서 JS 실행이 첫 화면 표시를 막는지 본다

재방문도 느리다
  -> 캐싱 헤더와 CDN 구성을 본다

스크롤이 버벅인다
  -> JS 긴 task와 이미지 lazy load 타이밍을 함께 본다
```

결국 좋은 최적화는 기술 이름을 많이 아는 것보다, 지금 느린 이유가 어느 비용에서 오는지 분리해서 보는 데서 시작한다.

## 공부할 때 추천하는 질문

마지막으로, 각 주제를 읽을 때 아래 질문을 계속 붙이면 공부가 훨씬 선명해진다.

```text
이 최적화는 다운로드 비용을 줄이는가
이 최적화는 실행 비용을 줄이는가
이 최적화는 첫 화면을 빠르게 하는가
이 최적화는 재방문을 빠르게 하는가
이 최적화는 지금 꼭 필요한 리소스의 우선순위를 높이는가
```

이 질문으로 다시 정리하면 이렇게 된다.

```text
텍스트 압축
  -> 다운로드 비용 감소

리소스 캐싱
  -> 재방문 비용 감소

preload
  -> 중요한 리소스 우선순위 조정

CDN
  -> 전달 거리와 지연 감소

이미지 최적화
  -> 큰 LCP 후보와 다운로드 비용 감소

lazy load
  -> 초기 비용 감소

code splitting
  -> 초기 JS 비용 감소

병목 코드 제거
  -> 실행 비용 감소
```

성능 최적화는 결국 "무엇을 늦게 받을 수 있는가"와 "무엇을 빨리 받아야 하는가", "무엇을 아예 덜 해야 하는가"를 구분하는 일이다.

다음에 실제 페이지를 볼 때는 이 글의 항목들을 체크리스트처럼 외우기보다, 먼저 병목을 찾고 그 병목이 네트워크, 이미지, JavaScript 중 어디에 속하는지부터 분류해보면 좋다. 그러면 각 기법이 왜 필요한지도 훨씬 덜 추상적으로 느껴진다.
