이번 시리즈는 pnpm 모노레포 안의 프론트엔드 앱을 Docker 이미지로 만들고, Docker Compose로 실행 환경을 고정한 뒤, Nginx를 이용해 blue-green 배포 구조로 확장하고, 마지막에는 Jenkins로 CI/CD 파이프라인까지 연결하는 과정을 기록한다.

완성된 구조를 먼저 그리면 이렇다.

```text
pnpm 모노레포
  -> 특정 앱 Docker 이미지 빌드
  -> Docker Compose 실행
  -> Nginx reverse proxy
  -> blue-green 슬롯 전환
  -> Jenkins CI/CD 자동화
```

이번 글은 **4편**이다. blue와 green 두 슬롯을 두고, 새 버전을 비활성 슬롯에 먼저 띄운 뒤 health check와 Nginx include 파일 전환으로 배포하는 흐름을 만든다.

Nginx가 앱 앞단에 있으면 트래픽을 어디로 보낼지 바꿀 수 있다. 이 성질을 이용하면 blue-green 배포를 연습할 수 있다.

blue-green 배포의 핵심은 단순하다.

```text
현재 서비스 중인 슬롯은 그대로 둔다.
반대 슬롯에 새 버전을 먼저 띄운다.
새 슬롯이 정상인지 확인한다.
Nginx가 새 슬롯을 보게 바꾼다.
이전 슬롯을 중지한다.
```

사용자는 Nginx만 바라보기 때문에, Nginx의 대상만 바뀌면 새 버전을 받게 된다.

## blue와 green은 두 개의 실행 자리다

이 저장소는 블로그 앱을 두 슬롯으로 나눈다.

```yaml
services:
  blog-blue:
    container_name: atelier-blog-blue
    image: ${BLOG_IMAGE:-atelier-blog:test}
    ports:
      - "127.0.0.1:3001:3000"

  blog-green:
    container_name: atelier-blog-green
    image: ${BLOG_IMAGE:-atelier-blog:test}
    ports:
      - "127.0.0.1:3002:3000"
```

둘 다 같은 앱을 실행할 수 있다. 차이는 이름과 포트뿐이다.

```text
blog-blue
  내 PC에서는 localhost:3001
  Compose 네트워크 안에서는 blog-blue:3000

blog-green
  내 PC에서는 localhost:3002
  Compose 네트워크 안에서는 blog-green:3000
```

운영 중에는 둘 중 하나만 active다. 나머지는 다음 배포를 받을 대기 슬롯이 된다.

## active include 파일

Nginx는 이 파일을 읽는다.

```text
infra/nginx/includes/blog-active.conf
```

이 파일이 blue를 가리키면 Nginx는 blue로 보낸다.

```nginx
upstream atelier_blog {
  server blog-blue:3000;
}
```

green을 가리키면 Nginx는 green으로 보낸다.

```nginx
upstream atelier_blog {
  server blog-green:3000;
}
```

blue-green 전환은 결국 이 active 파일을 바꾸는 일이다.

```text
blog-blue.conf -> blog-active.conf
또는
blog-green.conf -> blog-active.conf
```

그 다음 Nginx 설정을 검사하고 reload한다.

```bash
docker exec atelier-nginx nginx -t
docker exec atelier-nginx nginx -s reload
```

## 배포 스크립트가 하는 일

수동으로 하면 흐름을 이해하기 좋지만, 매번 사람이 하기에는 실수하기 쉽다. 그래서 배포 스크립트가 필요하다.

PowerShell 버전은 Windows 로컬에서 사용한다.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/deploy-blog-local.ps1 -Image localhost:5000/atelier-blog:manual-1 -Pull
```

Linux 버전은 Jenkins 컨테이너 안에서 사용한다.

```bash
bash scripts/deploy-blog-local.sh --image localhost:5000/atelier-blog:커밋해시 --pull
```

두 스크립트의 역할은 같다.

```text
1. active 파일을 읽어 현재 슬롯을 판단한다.
2. 반대 슬롯을 target으로 정한다.
3. 필요한 경우 이미지를 pull한다.
4. target 슬롯 컨테이너를 실행한다.
5. target 슬롯 health check를 기다린다.
6. active include 파일을 target 슬롯으로 바꾼다.
7. nginx 설정을 검사한다.
8. nginx reload를 실행한다.
9. 이전 슬롯 컨테이너를 중지한다.
```

로그로 보면 이런 모양이다.

```text
Current slot: blue
Target slot: green
Starting target container: atelier-blog-green
Waiting for health check: http://blog-green:3000/api/health
Switching active upstream to green
Validating nginx configuration
Reloading nginx
Stopping previous container: atelier-blog-blue
Blog deployment switched to green.
```

## health check가 전환보다 먼저다

blue-green 배포에서 가장 중요한 순서는 health check가 active 전환보다 앞에 있어야 한다는 점이다.

```text
나쁜 순서:
active 전환
  -> 새 컨테이너가 죽어 있음
  -> 사용자 502

좋은 순서:
새 컨테이너 실행
  -> health check 성공
  -> active 전환
```

블로그 앱에는 `/api/health`가 있다.

```json
{"ok":true,"app":"blog"}
```

배포 스크립트는 이 응답을 보고 새 슬롯이 실제로 요청을 받을 수 있는지 확인한다.

## localhost 함정

Jenkins에서 처음 CD를 붙였을 때 health check가 실패했다.

```text
Waiting for health check: http://127.0.0.1:3001/api/health
Health check failed
```

앱 컨테이너는 떠 있었는데 Jenkins는 health check를 실패로 봤다. 이유는 `127.0.0.1`의 기준이 달랐기 때문이다.

PowerShell에서 실행할 때 `127.0.0.1:3001`은 내 PC다. 그래서 Windows용 스크립트에서는 이 주소가 맞다.

```text
내 PC PowerShell
  127.0.0.1:3001 -> blog-blue 컨테이너
```

하지만 Jenkins는 컨테이너 안에서 실행된다. Jenkins 컨테이너 안에서 `127.0.0.1`은 Jenkins 컨테이너 자기 자신이다. blog 컨테이너가 아니다.

```text
Jenkins 컨테이너
  127.0.0.1 -> Jenkins 컨테이너
  blog-blue:3000 -> blog-blue 컨테이너
```

그래서 Linux용 배포 스크립트는 health check 주소를 서비스 이름 기준으로 둔다.

```bash
TARGET_HEALTH_URL="http://$TARGET_SERVICE:3000/api/health"
```

이 차이를 모르면 컨테이너는 정상인데 health check만 실패하는 상황을 만난다.

## 실패 중간 상태 복구

실습 중 실패가 나면 중간 상태가 남을 수 있다.

예를 들어 active 파일은 green을 보고 있는데 green 컨테이너는 꺼져 있고 blue만 살아 있으면 Nginx는 502를 낸다.

```text
active: green
running: blue
결과: nginx 502
```

이때는 살아 있는 슬롯으로 active 파일을 되돌리고 Nginx를 reload하면 된다.

```powershell
Copy-Item C:\study\atelier\infra\nginx\includes\blog-blue.conf C:\study\atelier\infra\nginx\includes\blog-active.conf -Force
docker exec atelier-nginx nginx -s reload
```

복구 후 다음 배포를 다시 실행하면 반대 슬롯으로 전환된다. 이 과정 자체가 blue-green 구조를 이해하는 데 도움이 된다.

## 정리

blue-green 배포는 특별한 마법이 아니다. 두 개의 실행 슬롯과 하나의 트래픽 스위치다.

```text
blue 슬롯
green 슬롯
Nginx active include 파일
health check
reload
```

전환 순서만 지키면 된다.

```text
현재 슬롯 유지
  -> 반대 슬롯 실행
  -> health check
  -> active include 전환
  -> nginx reload
  -> 이전 슬롯 중지
```

이제 남은 일은 이 과정을 사람이 직접 실행하지 않게 만드는 것이다. 다음 글에서는 Jenkins가 코드 검증, 이미지 빌드, registry push, blue-green 배포 스크립트 실행을 맡는 CI/CD 파이프라인을 만든다.
