앞 글에서 그룹에 정책을 붙여 권한을 부여하는 흐름을 봤다.  
이번에는 정책을 더 깊게 본다. 정책이 **어떻게 적용·상속되는지**와 **정책 JSON의 구조**를 먼저 정리하고, 이어서 콘솔에서 정책을 직접 붙였다 떼며 권한 변화를 실습한다.

## 정책 상속

정책은 보통 **그룹 레벨**에 연결한다. 그러면 그룹의 모든 구성원이 그 정책을 상속한다.

- `Developers` 그룹(Alice, Bob, Charles)에 정책을 붙이면 셋 모두 권한을 얻는다.
- `Operations` 그룹(David, Edward)에는 다른 정책을 붙인다.

그룹에 속하지 않은 사용자(예: Fred)도 있을 수 있다. 이때는 **인라인 정책(inline policy)** 을 만들어 사용자에게 직접 붙인다. 인라인 정책은 그룹 소속 여부와 무관하게 원하는 사용자에게 적용할 수 있다.

한 사용자가 여러 그룹에 속하면 **각 그룹의 정책을 모두 상속**한다. Charles와 David가 `Audit` 그룹에도 속한다고 하면 결과는 다음과 같다.

```text
Developers 그룹  : Alice, Bob, Charles   -> 그룹 정책 상속
Operations 그룹  : David, Edward         -> 그룹 정책 상속
Audit 그룹       : Charles, David        -> 그룹 정책 상속

Fred             : 그룹 없음 -> 인라인 정책(사용자에 직접 연결)

결과
  Charles -> Developers 정책 + Audit 정책
  David   -> Operations 정책 + Audit 정책
```

## 정책 JSON 구조

정책은 JSON 문서다. AWS에서 자주 보게 되는 형식이므로 구조와 명명에 익숙해져야 한다. 모든 요소를 담은 예시는 다음과 같다.

```json
{
  "Version": "2012-10-17",
  "Id": "S3-Account-Permissions",
  "Statement": [
    {
      "Sid": "1",
      "Effect": "Allow",
      "Principal": {
        "AWS": ["arn:aws:iam::123456789012:root"]
      },
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": ["arn:aws:s3:::my-bucket/*"]
    }
  ]
}
```

위 예시를 풀어 읽으면 이렇다.

```text
이 정책은
  -> 계정 123456789012 의 루트 계정(Principal)에게
  -> my-bucket 버킷의 객체(Resource)에 대해
  -> 읽기(s3:GetObject)와 쓰기(s3:PutObject) 작업(Action)을
  -> 허용(Allow, Effect)한다.
```

`Condition`은 선택이지만 자주 쓰인다. 예를 들어 특정 IP 대역에서만 허용하려면 다음처럼 붙인다.

```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": {
    "IpAddress": {
      "aws:SourceIp": "203.0.113.0/24"
    }
  }
}
```

## 시험 포인트

정책 구조에서 반드시 확실히 이해하고 있어야 하는 네 가지는 다음과 같다.

```text
Effect    -> 허용(Allow)인가 거부(Deny)인가
Principal -> 누구에게 적용되는가
Action    -> 어떤 API 호출인가
Resource  -> 어떤 리소스에 적용되는가
```

---

여기까지가 구조와 상속이다. 이제 콘솔에서 정책을 직접 다뤄 본다. 실습은 두 창을 띄워 둔 상태로 진행한다(왼쪽 루트 계정, 오른쪽 IAM 사용자 `Stephane`).

## 권한을 잃어보기

`Stephane`은 `admin` 그룹에 속해 있어 **AdministratorAccess**를 가진다. 즉 무엇이든 할 수 있다.

이 상태에서 루트 창에서 `admin` 그룹에 들어가 **Stephane을 그룹에서 제거**한다. 그러면 오른쪽 Stephane 창에서 권한을 잃는다. 페이지를 새로고침하면 결과가 바로 보인다.

```text
Users 목록이 비어 있고 "액세스 거부"
  -> iam:ListUsers 권한이 없다는 메시지
  -> admin 그룹에서 빠지면서 그룹 권한을 모두 잃었기 때문
```

그룹에서 빠지면 그 그룹이 주던 권한도 함께 사라진다는 점을 보여 준다.

## 사용자에 정책 직접 첨부

권한을 다시 주는 방법은 세 가지다.

```text
1) 사용자를 그룹에 추가      (그룹 권한을 상속)
2) 관리형 정책을 직접 첨부    (이번에 사용하는 방법)
3) 인라인 정책 생성          (사용자에만 붙는 정책)
```

여기서는 더 간단한 **직접 첨부**를 쓴다. Stephane(권한 정책 0개)에 **IAMReadOnlyAccess**를 첨부하면, IAM의 모든 것을 읽을 수 있게 된다. 오른쪽 창을 새로고침하면 다시 API 호출이 되고 사용자 목록에서 Stephane이 보인다.

## 최소 권한 확인

읽기 권한만 있는 상태에서 그룹을 만들 수 있을까? `Create group`을 누르면 **생성할 수 없다**고 나온다. 지금은 IAM 읽기 전용 권한만 있기 때문이다.

그룹을 만들려면 `IAMFullAccess` 같은 **더 큰 권한**을 붙여야 한다. 이 동작이 보여 주는 것은, 사용자에게는 **할 일에 필요한 권한만** 준다는 최소 권한의 원칙이다.

## 세 가지 경로로 붙은 권한

이번엔 권한이 여러 경로로 쌓이는 모습을 본다.

1. `developers` 그룹을 만들고 아무 정책(예: `AlexaForBusiness`)을 붙인 뒤 Stephane을 추가한다.
2. `admin` 그룹에도 Stephane을 다시 추가한다.

이제 Stephane을 보면 권한 정책 세 개가 **서로 다른 경로**로 붙어 있다.

## 관리형 정책 뜯어보기

정책을 누르면 요약과 JSON을 볼 수 있다. 먼저 **AdministratorAccess**의 JSON이다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "*",
      "Resource": "*"
    }
  ]
}
```

AWS에서 `*`는 **anything(아무것이나)** 를 뜻한다. 즉 "어느 리소스(`Resource: *`)에서든 어느 액션(`Action: *`)이든 허용"이며, 이것이 곧 관리자 권한이다.

다음은 **IAMReadOnlyAccess**다(핵심만 간추린 형태).

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "iam:Get*",
        "iam:List*"
      ],
      "Resource": "*"
    }
  ]
}
```

여기서 `*`는 **와일드카드**로 쓰여 여러 API 호출을 한 번에 묶는다.

```text
iam:Get*   -> Get 으로 시작하는 모든 호출 (GetUser, GetGroup ...)
iam:List*  -> List 로 시작하는 모든 호출 (ListUsers, ListGroups ...)
Resource:* -> 모든 IAM 리소스에 대해
```

읽기(`Get`, `List`)만 허용하므로 조회는 되지만 생성·수정은 안 된다. 앞서 그룹 생성이 막힌 이유다.

## 커스텀 정책 만들기

직접 정책을 만들 수도 있다. **Visual 편집기**나 **JSON 편집기** 중 고른다. JSON이 이미 있다면 JSON 편집기에 붙여 넣어 수정하면 되고, 없다면 Visual 편집기로 클릭하며 만든다.

Visual 편집기 흐름은 이렇다.

```text
서비스 선택      -> IAM
액션 선택        -> ListUsers (List 38개 중 1개), GetUser (Read 32개 중 1개)
리소스 범위 선택 -> 모든 리소스 또는 특정 리소스
이름 지정        -> MyIAMPermissions
```

만들어진 정책의 JSON은 다음과 같다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "VisualEditor0",
      "Effect": "Allow",
      "Action": [
        "iam:GetUser",
        "iam:ListUsers"
      ],
      "Resource": "*"
    }
  ]
}
```

이 정책은 그룹이나 사용자에 첨부할 수 있다. 이렇게 필요한 액션만 골라 권한을 직접 정의할 수 있다.

## 원상 복구

실습에서 만든 것을 정리한다.

```text
developers 그룹 삭제
직접 첨부한 IAMReadOnlyAccess 제거
  -> Stephane 은 admin 그룹에만 속함
  -> AdministratorAccess 만 보유
```

IAM 콘솔의 Users로 들어가 모든 항목이 정상적으로 보이면 복구가 끝난 것이다.

## 정리

```text
[정책 상속]
  -> 그룹에 정책을 붙이면 구성원 전체가 상속
  -> 그룹 미소속 사용자 -> 인라인 정책으로 직접 연결
  -> 여러 그룹 소속 시 각 그룹 정책을 모두 상속

[정책 JSON 구조]
  Version / Id / Statement(Sid·Effect·Principal·Action·Resource·Condition)
  시험 핵심 -> Effect, Principal, Action, Resource

[실습]
  권한 상실/복구 -> 그룹에서 빠지면 그룹 권한도 사라짐, 다시 주는 법 3가지
  최소 권한      -> 읽기 전용으론 생성 불가, 필요한 권한만
  권한 누적      -> 그룹 상속 + 직접 첨부가 모두 합쳐져 적용
  관리형 정책    -> AdministratorAccess(Action·Resource "*") / IAMReadOnlyAccess(Get*·List*)
  커스텀 정책    -> Visual / JSON 편집기로 필요한 액션만 골라 생성 후 첨부
```
