Git을 공부할 때 제일 헷갈리는 순간 중 하나가 바로 이런 질문이 나올 때다.

```text
되돌리고 싶으면 revert지?
아니면 reset인가?
rebase는 merge랑 뭐가 다르지?
checkout은 왜 restore랑 switch로 갈라졌지?
```

명령어 이름만 외우면 금방 섞인다. 그래서 Git은 명령 하나씩 따로 암기하기보다, 먼저 **무엇을 바꾸는 명령인지** 기준으로 지도를 그려두는 편이 훨씬 낫다.

이 글은 그 지도를 먼저 그리고, 그다음에 가장 많이 헷갈리는 `rebase`와 `revert`를 중심으로 살펴본다. 마지막에는 팀에서 실제로 많이 쓰는 Git 전략까지 같이 묶어보겠다.

## 먼저 큰 그림부터

Git 명령어는 대충 아래 네 부류로 나눠서 보면 덜 헷갈린다.

<GitCommandAtlasDiagram />

```text
1. 이력을 합치거나 옮기는 명령
   merge, rebase, cherry-pick

2. 작업 내용을 되돌리거나 치우는 명령
   revert, reset, restore

3. 위치를 바꾸는 명령
   switch, checkout

4. 기록을 만드는 명령
   add, commit, stash
```

이제 아주 단순한 브랜치 그림 하나를 보자.

```text
main:    A --- B --- C
                    \
feature:             D --- E
```

여기서 우리가 보통 하는 고민은 몇 가지로 줄어든다.

```text
feature를 main에 합칠까?          -> merge
feature를 main 위로 다시 얹을까?  -> rebase
D만 다른 브랜치로 가져올까?       -> cherry-pick
이미 머지된 E를 취소할까?         -> revert
아직 안 밀어둔 D, E를 지울까?      -> reset
작업 파일만 원래대로 돌릴까?       -> restore
```

<Callout title="명령어를 보기 전에 먼저 질문을 고르자">
Git에서 중요한 건 명령어 이름보다 질문이다. 히스토리를 남긴 채 취소하고 싶은지, 아예 브랜치 모양을 다시 정리하고 싶은지, 아니면 작업 파일만 버리고 싶은지를 먼저 고르면 그다음 명령이 자연스럽게 따라온다.
</Callout>

## rebase와 revert는 아예 다른 문제를 푼다

둘 다 "과거를 건드린다"는 느낌 때문에 비슷해 보이지만, 실제로는 해결하는 문제가 다르다.

### `rebase`: 브랜치의 기반을 옮긴다

`rebase`는 말 그대로 **어디 위에서 작업한 것처럼 보이게 다시 얹는 명령**이다.

처음 상태가 이렇다고 해보자.

```text
main:    A --- B --- C
                    \
feature:             D --- E
```

그 사이 `main`에 새 커밋 `F`가 들어왔다.

```text
main:    A --- B --- C --- F
                    \
feature:             D --- E
```

이때 `feature`에서 `git rebase main`을 하면 보통 이렇게 이해하면 된다.

```text
1. D, E를 잠깐 떼어 둔다
2. feature의 시작점을 F 뒤로 옮긴다
3. D, E를 F 뒤에 다시 적용한다
```

결과 모양은 이렇게 된다.

```text
main:    A --- B --- C --- F
                           \
feature:                    D' --- E'
```

여기서 중요한 점은 `D`, `E`가 그대로 이동한 것이 아니라 **새 커밋 `D'`, `E'`로 다시 만들어진다**는 점이다. 그래서 `rebase`는 히스토리 자체를 다시 쓰는 명령이라고 말한다.

### `revert`: 이미 들어간 변경을 반대 커밋으로 취소한다

`revert`는 히스토리를 예쁘게 정리하는 명령이 아니다. 대신 **이미 반영된 변경을 안전하게 취소하는 기록을 하나 더 남기는 명령**이다.

예를 들어 `main`이 이렇다고 해보자.

```text
main: A --- B --- C --- D
```

여기서 `C`가 문제라면 `git revert C`는 대충 이렇게 작동한다.

```text
main: A --- B --- C --- D --- R
```

`R`은 "C의 반대 작업"을 담은 새 커밋이다. 즉 `C`를 지워버리는 게 아니라, **C를 취소했다는 이력까지 남기는 방식**이다.

그래서 `revert`는 특히 이미 원격에 push해서 다른 사람과 공유한 브랜치에서 많이 쓴다.

## 둘의 차이를 한 번에 잡는 비교표

아래 표처럼 보면 감이 훨씬 빨리 온다.

```text
rebase
  - 목적: 브랜치 기반 이동, 히스토리 정리
  - 결과: 기존 커밋이 새 커밋으로 다시 만들어질 수 있음
  - 이력 변경: 큼
  - 주 사용처: 개인 브랜치 정리, 머지 전 선형 히스토리 만들기
  - 공유 브랜치 사용: 조심해야 함

revert
  - 목적: 이미 반영된 변경 취소
  - 결과: 취소용 새 커밋 추가
  - 이력 변경: 기존 이력은 보존
  - 주 사용처: 운영 브랜치, 공유 브랜치에서 안전한 롤백
  - 공유 브랜치 사용: 안전한 편
```

핵심은 이 한 줄이다.

```text
rebase는 히스토리의 모양을 다시 만든다
revert는 히스토리를 남긴 채 결과를 되돌린다
```

## 언제 rebase를 쓰고, 언제 revert를 쓰는가

### `rebase`가 잘 맞는 상황

- 아직 나만 쓰는 `feature` 브랜치다.
- `main` 최신 커밋 위로 작업을 다시 얹고 싶다.
- PR 전에 커밋 흐름을 깔끔하게 정리하고 싶다.
- 중간의 `fix typo`, `oops`, `address review` 같은 잡커밋을 묶고 싶다.

이때 많이 쓰는 명령은 이런 느낌이다.

```bash
git switch feature
git fetch origin
git rebase origin/main
```

혹은 커밋을 정리하고 싶으면 인터랙티브 리베이스를 쓴다.

```bash
git rebase -i HEAD~4
```

이 명령은 최근 4개 커밋을 다시 배열하거나 합치거나 메시지를 고칠 때 쓴다.

### `revert`가 잘 맞는 상황

- 이미 `main`에 머지되었다.
- 이미 push해서 다른 사람도 그 이력을 보고 있다.
- 문제를 빠르게 되돌리고 싶다.
- "무엇을 왜 취소했는지" 흔적을 남겨야 한다.

예를 들어 운영 장애를 낸 커밋이 하나 있다면 보통 `revert`가 더 안전하다.

```bash
git revert <commit>
```

머지 커밋을 되돌릴 때는 부모를 지정해야 해서 조금 더 조심한다.

```bash
git revert -m 1 <merge-commit>
```

## merge, rebase, cherry-pick은 어떻게 다른가

이 셋도 자주 같이 헷갈린다. 전부 "커밋을 가져와 합친다"는 느낌이 있기 때문이다.

<GitMergeRebaseCherryPickDiagram />

### `merge`: 두 줄기의 역사를 그대로 합친다

처음 상태:

```text
main:    A --- B --- C
                    \
feature:             D --- E
```

`git merge feature` 결과:

```text
main:    A --- B --- C -------- M
                    \         /
feature:             D --- E --
```

`merge`는 두 갈래의 역사를 그대로 보존한다. 협업 흔적이 남고, 이해하기 쉬운 대신 히스토리가 복잡해질 수 있다.

### `rebase`: 내 커밋을 최신 기반 위에 다시 놓는다

```text
main:    A --- B --- C --- F
                           \
feature:                    D' --- E'
```

히스토리가 선형에 가까워져서 읽기 편하지만, 커밋 ID가 바뀌므로 공유 브랜치에서는 주의가 필요하다.

### `cherry-pick`: 특정 커밋만 골라 가져온다

```text
main:    A --- B --- C
feature:      \ 
               D --- E --- F

main에서 E만 필요:

main:    A --- B --- C --- E'
feature:      \ 
               D --- E --- F
```

브랜치 전체를 합치고 싶지는 않은데, 특정 수정 하나만 급하게 가져오고 싶을 때 유용하다. 핫픽스를 다른 릴리스 브랜치로 옮길 때 자주 쓴다.

## reset, restore, checkout은 왜 자꾸 헷갈릴까

이 셋은 "되돌린다"는 느낌이 있어서 자주 섞이는데, 실제로 건드리는 대상이 다르다.

<GitResetRestoreDiagram />

### `reset`: 브랜치의 가리키는 위치를 옮긴다

```text
main: A --- B --- C --- D
                    ^
                  HEAD
```

여기서 `git reset --hard B`를 하면:

```text
main: A --- B
```

브랜치가 `B`를 가리키게 된다. `C`, `D`는 현재 브랜치 이력에서 떨어진다. 그래서 **강한 되감기**에 가깝다.

자주 보는 세 가지는 이런 느낌이다.

```text
git reset --soft  <target>
  - 커밋만 취소
  - 스테이징과 작업 파일은 남김

git reset --mixed <target>
  - 커밋과 스테이징 취소
  - 작업 파일은 남김

git reset --hard  <target>
  - 커밋, 스테이징, 작업 파일까지 target 기준으로 맞춤
```

특히 `--hard`는 위험하다. 아직 push하지 않은 개인 브랜치 정리에 주로 쓰고, 공유 브랜치에서는 대개 피한다.

### `restore`: 작업 파일이나 스테이징만 되돌린다

`restore`는 비교적 현대적인 Git에서 "파일 상태를 원래대로 돌리는 역할"을 분리해둔 명령이다.

```bash
git restore src/app.ts
git restore --staged src/app.ts
```

대충 이렇게 이해하면 된다.

```text
restore
  - 파일 내용만 되돌리고 싶다
  - 스테이징만 빼고 싶다
  - 브랜치 히스토리 자체는 안 건드리고 싶다
```

### `checkout`과 `switch`

예전에는 `checkout`이 너무 많은 일을 했다.

```text
브랜치 이동도 checkout
파일 복원도 checkout
특정 커밋 보기에도 checkout
```

그래서 Git이 역할을 나눴다.

```text
브랜치 이동     -> switch
파일 복원       -> restore
옛 방식 만능칼  -> checkout
```

요즘은 보통 이렇게 쓰면 덜 헷갈린다.

```bash
git switch feature
git restore src/app.ts
```

## 공부할 때 자주 보는 Git 명령어 지도

아래 지도처럼 보면 어떤 질문에 어떤 명령이 붙는지 빨리 연결된다.

```text
브랜치를 합치고 싶다
  -> merge

브랜치를 최신 기반 위로 다시 얹고 싶다
  -> rebase

특정 커밋만 옮기고 싶다
  -> cherry-pick

이미 반영된 변경을 안전하게 취소하고 싶다
  -> revert

아직 안 밀어둔 커밋을 뒤로 되감고 싶다
  -> reset

작업 파일만 원래대로 돌리고 싶다
  -> restore

브랜치를 바꾸고 싶다
  -> switch

작업 중이던 걸 잠깐 치워두고 싶다
  -> stash
```

## 실무에서 많이 보는 Git 전략들

명령어를 아는 것과 팀 전략을 이해하는 것은 조금 다르다. 명령어는 손의 문제고, 전략은 팀이 히스토리를 어떤 형태로 관리할지에 대한 합의에 가깝다.

<GitStrategyDiagram />

### 1. Git Flow

가장 전통적인 전략 중 하나다.

```text
main      : 운영 배포 이력
develop   : 다음 릴리스 통합
feature/* : 기능 개발
release/* : 출시 준비
hotfix/*  : 운영 긴급 수정
```

도식은 대충 이렇게 생긴다.

```text
main:    A ----------- R ----------- H
            \           \             \
develop:     B --- C --- D --- E --- F
                \       \       \
feature/*        x       y       z
```

장점은 역할이 분명하다는 점이다. 단점은 브랜치가 많아지고 운영 속도가 느려질 수 있다는 점이다. 배포 주기가 길고 릴리스 관리가 엄격한 조직에서는 아직도 잘 맞는다.

### 2. GitHub Flow

조금 더 단순하다.

```text
main      : 항상 배포 가능한 상태
feature/* : 기능 브랜치
PR        : 리뷰 후 main으로 머지
배포       : main 기준
```

도식은 이렇다.

```text
main:    A --- B --- C --- D --- E
              \     \       \
feature/x      x1 --- x2
feature/y            y1 --- y2
hotfix/z                     z1
```

핵심은 `main`을 항상 건강하게 유지하는 것이다. SaaS처럼 자주 배포하는 팀에 잘 맞는다. 구조가 단순해서 작은 팀이나 빠른 제품 팀이 많이 쓴다.

### 3. Trunk-Based Development

더 극단적으로 단순한 전략이다. 긴 생명주기 브랜치를 최소화하고, 아주 짧은 브랜치 또는 직접 `trunk`에 가깝게 통합한다.

```text
trunk(main): A --- B --- C --- D --- E --- F
                \   \   \   \
short branch     x   y   z   h
```

핵심 원칙은 보통 이렇다.

- 브랜치는 아주 짧게 산다.
- 자주 통합한다.
- 기능 플래그를 적극적으로 쓴다.
- 큰 기능도 작게 쪼개서 자주 머지한다.

CI가 빠르고 테스트 자동화가 잘 되어 있는 팀에 특히 잘 맞는다. 반대로 테스트와 배포 안전장치가 약하면 부담이 커질 수 있다.

### 4. Release Branch 전략

운영 버전과 다음 버전을 동시에 관리해야 할 때 자주 본다.

```text
main:         A --- B --- C --- D
                    \
release/1.0          R1 --- R2
                              \
hotfix               H1 -------H2
```

모바일 앱, 온프레미스 배포, 고객사별 버전 유지처럼 "여러 릴리스를 병행 관리"해야 할 때 유용하다. 대신 브랜치 관리 복잡도가 높아진다.

## 어떤 전략이 어떤 팀에 맞을까

정답은 없지만 대략 이런 식으로 감을 잡을 수 있다.

```text
작고 빠른 제품 팀
  -> GitHub Flow, Trunk-Based Development

배포가 자주 일어나고 CI가 강한 팀
  -> Trunk-Based Development

릴리스 단계가 길고 승인 절차가 많은 팀
  -> Git Flow, Release Branch 전략

여러 버전을 동시에 유지해야 하는 팀
  -> Release Branch 전략
```

중요한 건 "어떤 전략이 더 고급인가"가 아니다. 팀의 배포 주기, 테스트 자동화 수준, 리뷰 문화에 맞느냐가 더 중요하다.

<Callout title="좋은 Git 전략은 멋진 전략이 아니라 사고를 줄이는 전략이다">
팀이 감당할 수 없는 복잡한 전략은 오래 못 간다. 브랜치를 화려하게 나누는 것보다, 지금 팀이 자주 하는 작업을 가장 덜 헷갈리게 만드는 전략이 더 좋은 전략이다.
</Callout>

## 실무 감각으로 정리하면

공부할 때는 아래 감각을 먼저 잡아두면 도움이 된다.

```text
내 개인 브랜치 정리
  -> rebase, reset 자주 등장

공유된 브랜치에서 안전한 취소
  -> revert 자주 등장

브랜치 전체 통합
  -> merge 또는 rebase 후 merge

특정 수정만 다른 곳으로 이동
  -> cherry-pick

파일만 되돌리기
  -> restore
```

그리고 `rebase`와 `revert`는 아래처럼 기억하면 오래 간다.

```text
rebase
  - 선을 다시 그린다
  - 커밋의 기반과 모양을 바꾼다
  - 깔끔하지만 공유 이력에서는 조심

revert
  - 잘못 그린 선 위에 취소선을 하나 더 긋는다
  - 기존 이력은 남긴다
  - 협업 브랜치에서 안전한 편
```

## 마지막 한 장 요약

정말 마지막으로, 시험 직전 치트시트처럼 한 번만 더 줄이면 이렇다.

```text
merge
  - 브랜치 두 줄기를 합친다

rebase
  - 내 커밋을 다른 기반 위에 다시 얹는다

revert
  - 기존 커밋을 취소하는 새 커밋을 만든다

reset
  - 브랜치 위치를 뒤로 돌린다

restore
  - 파일 상태를 되돌린다

switch
  - 브랜치를 이동한다

cherry-pick
  - 특정 커밋만 골라 가져온다

stash
  - 지금 작업을 잠깐 서랍에 넣어둔다
```

Git은 명령어가 많아 보여도 결국 세 가지를 구분하면 훨씬 쉬워진다.

```text
히스토리를 다시 쓰는가?
히스토리를 남긴 채 취소하는가?
파일만 되돌리는가?
```

이 셋만 구분해도 `rebase`, `revert`, `reset`, `restore`가 한꺼번에 정리된다. 그리고 그 위에 팀 전략을 얹으면, 이제 Git은 "명령어 암기"보다 "이력 설계"에 가까운 도구로 보이기 시작한다.
